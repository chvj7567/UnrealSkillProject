# 오브젝트 상호작용 미션 — 콘텐츠 기획

> **이 문서의 범위**: `ESpyMissionType::Interact` 타입 미션 1건의 **콘텐츠 결정**(플레이어 체감·`DA_SpyMissionConfig` 검증용 엔트리 값·`InteractVerb` 문구·오브젝트 배치)만 다룬다.
> 클래스 구조(`ASpyInteractableObject`/`ISpyInteractableRoot`)·RPC 흐름·레플리케이션 방식·`FSpyMissionEntry` 스키마는 [spec](../superpowers/specs/2026-08-03-interactable-object-mission-design.md) 과 [plan](../superpowers/plans/2026-08-03-interactable-object-mission.md) 이 이미 확정했다. 이 문서는 그것을 다시 제안하지 않고 인용만 한다.
> **승인 상태**: 작업 지시 기준 spec 은 **사용자 승인 완료**로 취급한다. ⚠ spec 파일 자체 헤더(5행)는 "브레인스토밍 완료, 사용자 승인 대기"로 남아 있어 문서 상태가 갱신되지 않은 것으로 보인다 — 승인 완료 쪽을 현재 상태로 채택하고, 헤더 정정은 이 기획서 범위 밖이다.
> **선행 시스템**: [미션 시스템](mission-system.md)(6종 미션·보상 스케일·배치 원칙의 단일 진실), [NPC 대화 기반 미션 spec](../superpowers/specs/2026-08-01-npc-mission-dialogue-design.md)(현재 라이브 코드가 구현한 12행 체인·`MissionReward` 관계 테이블 구조 — `SpyMissionComponent.cpp` 실측으로 확인).
> **(2026-08-03 후속 결정으로 인덱스/ID 표기 갱신됨)** 이 문서는 미션 데이터가 `Missions` 배열·0-based `index`이던 시점에 작성됐다. 이후 별도 결정으로 `DA_SpyMissionConfig::MissionTable`(DataTable) + 명시적 `MissionId`(1-based, 1~12)로 전환됐다 — 상세는 `docs/design/npc-mission-dialogue.md` 참조. 아래 §1·§3-1·§3-4의 인덱스/ID 표기를 그에 맞춰 정정했다.

- **목표** — 레벨에 배치된 단일 오브젝트를 F키로 1회 상호작용해 완료되는 `Interact` 미션 1건의 콘텐츠 값을 확정하고, 이 미션 타입이 만드는 플레이어 체감을 NPC 대화형과 구분해 정의한다.
- **검증 가설** — (1) 대사 없는 "조용한 조사형" 상호작용이 대화형 미션과 구별되는 리듬으로 읽히는가. (2) 1회성 소진 오브젝트 1개로 미션 진행도가 정확히 갱신되는가 — 이번 최소 기능의 검증 대상은 이 두 가지이며, 콘텐츠 다량 제작이나 밸런스 최종안은 대상이 아니다.
- **현재 단계 범위 적합성** — `.claude/project.md` 의 `stage`/`stage_goal` 과 컨셉서(`spyproject_concept.md`) §2·§4·§5 는 전부 **(사용자 확정 대기)** 다. 따라서 이 기획서는 프로젝트 단계 부합 여부를 단정하지 않는다. 대신 **spec §1 의 목표·비목표를 범위 경계로 삼는다** — spec 이 명시한 비목표(DevMap 실배치·다중 오브젝트·인벤토리 연동·재사용 가능 오브젝트)는 §11 에 그대로 명시 제외로 남긴다.
- **핵심 메커니즘** — `TargetCount` 는 배치한 오브젝트 개수와 일치해야 한다(이번 검증은 오브젝트 1개 → `TargetCount = 1`, §3-2). 상호작용 즉시 진행도가 조용히 갱신되고 오브젝트는 콜리전이 꺼져 재상호작용이 불가능해진다. NPC 대화형과 달리 카드·대사 없이 "확인 즉시 완료"라는 점이 체감의 핵심이다.

## §2 플레이어 경험 서술

| 축 | NPC 대화형(`Dialogue`) | 오브젝트 상호작용형(`Interact`) |
|---|---|---|
| 트리거 | NPC 근접 + F → 대화 UI 오픈 → 확인/보고 | 오브젝트 근접 + F → **UI 없이 즉시** 진행도 갱신 |
| 정보량 | 대사 텍스트로 서사 전달("정리는 끝났나, 수고했다") | 텍스트 0 — 침묵. 서사는 오브젝트의 **존재와 배치 자체**로 전달 |
| 반복성 | NPC 는 소진되지 않는다(계속 그 자리에서 다음 역할로 남음) | 오브젝트는 1회성 — 상호작용 직후 다시 찾아가면 콜리전이 꺼져 있어 "이미 끝났다"는 사실이 물리적으로 드러남 |
| 체감 축 | **정보 수집형** — 사람에게 듣는다 | **조사형** — 현장에서 직접 확인·조작한다 |
| 적합한 순간 | 브리핑·보고·다음 목표 지시 | 단서 확인, 장치 조작, 잠입 중 스위치 조작처럼 "말이 필요 없는 확인 행위" |

이 구분이 성립하려면 두 가지가 지켜져야 한다:
1. `InteractVerb` 가 "대화하기"와 겹치지 않아야 한다(§4).
2. 오브젝트 상호작용에 확인 카드(§NPC spec 의 `MissionOffer` 류)를 절대 씌우지 않는다 — spec 이 이미 이렇게 확정했고(`Interact` 도 `Dialogue` 와 같은 자동 수락 부류), 이 기획서는 이걸 유지 요청으로만 남긴다.

### 3-2. `TargetCount` — 배치한 오브젝트 개수와 일치해야 한다 (이번 검증은 1)

**정정(사용자 지적)**: 이전 판의 "구조적으로 강제된다"는 표현은 마치 엔진·설계가 `TargetCount = 1` 만 허용하는 것처럼 읽혀 오해를 줬다. 실제로는 그렇지 않다 — `ResolveMissionProgress`(`Accumulate` 모드)는 `MatchTag` 가 일치하는 이벤트 **횟수**만 누적할 뿐, 그 이벤트가 어느 오브젝트에서 왔는지는 구분하지 않는다(spec §2-3, 순수 함수). 같은 `MissionEventTag` 를 가진 오브젝트를 **N개** 배치하면 `TargetCount = N` 도 정상 동작한다(예: 오브젝트 2개 배치 시 `TargetCount = 2`).

**이번 검증에서 1인 이유**: 오브젝트는 1회성 소진이라(§1) 오브젝트 1개가 평생 낼 수 있는 이벤트는 정확히 1번이다(상호작용 직후 `bConsumed = true` 로 콜리전이 꺼져 같은 오브젝트로는 두 번째 `AddProgress` 호출이 발생할 수 없다). 이번 검증은 spec §1 목표대로 **오브젝트 1개만 배치**하므로, `TargetCount` 는 그 배치 개수(1)와 일치해야 한다 — `TargetCount ≥ 2` 로 두면 두 번째 이벤트를 낼 오브젝트가 없어 진행도가 1/2 에서 **영구히 멈춘다.**

**일반 규칙**: `TargetCount = 이번 계획에서 배치하는(같은 MissionEventTag 를 가진) 오브젝트 개수`. 이번 §3 의 값(1)은 검증 범위가 오브젝트 1개이기 때문에 나온 결과이지, 시스템이 1 만 허용해서가 아니다 — 정식 콘텐츠로 오브젝트를 여러 개 배치하면 그 개수에 맞춰 `TargetCount` 를 올리면 된다.

### 3-3. 체인 위치 — 맨 끝, PIE 검증 후 제거되는 임시 엔트리

**수명 — 임시(BLOCKER 정정)**: 이 엔트리는 plan Task 6 Step 6 이 명시하는 "임시 미션 엔트리"다. plan 은 "완료 후 남는 것" 섹션에서 "**실제 콘텐츠용** `Interact` 타입 미션 엔트리 추가"를 이번 6개 태스크와 분리된 **별도의 미래 작업**으로 명시했다 — 즉 이번 plan 이 짜 놓은 구도는 "검증용 엔트리를 넣어 PIE 로 §9 의 D1~D3 를 확인한 뒤 지운다"이지, 체인에 영구 상주시키는 것이 아니다. 이 기획서의 이전 판은 이를 영구 편입 전제로 서술했다 — 이번 개정에서 plan 의 전제로 정정한다.

**배치 근거는 여전히 유효**: mission-system.md §2-4 가 그래플 미션을 맨 뒤에 둔 이유(조작 난이도·**선행 에셋 조건에 대한 실패 격리**)를 그대로 적용한다. `Interact` 미션은 DevMap 실배치(오브젝트 위치·`MissionEventTag` 지정)라는, 이번 범위에서 사용자가 별도로 수행할 선행 조건에 의존한다(spec §7 "에셋" 항목). 맨 끝에 두면 이 조건이 아직 안 끝났거나 잘못돼도 **앞선 12개 미션은 영향을 받지 않고 정상 관측된다.**

**영구 부작용 없음**: 검증 기간에만 존재했다 제거되므로(§8 조건표 #3), 보상 총합 재계산이나 "완주 시점 = 만렙 도달" 페이싱 어긋남 같은 **영구적 영향은 발생하지 않는다** — 넣었다 빼는 것뿐이다. 정식 콘텐츠로 이 미션 타입을 편입하는 결정은 이번 plan 범위 밖의 별도 미래 작업이며, 그 시점에 위치·보상·§7-1 재산출 트리거를 다시 정한다. 지금 이 기획서는 그 결정을 내리지 않는다.

### 3-4. `DT_SpyMissionReward` 보상 행 (검증 기간 한정)

| 필드 | 값 |
|---|---|
| `MissionId` | 13 (§3-1 과 동일 값으로 맞춘다 — 어긋나면 `GetMissionReward()` 가 이 행을 못 찾아 `0.f` 반환 + 경고 로그) |
| `ExperienceReward` | **10** |

**근거**: mission-system.md §3-3 의 보상 스케일 — "전투 구역 3종(짧고 즉각적) = 10, 이동 구역 2종(1회 소요 시간이 긴 반복 행동) = 15". 오브젝트 상호작용은 `TargetCount = 1` 로 반복이 없고 상호작용 자체(F 1회)는 즉각적이다 — 이동/탐색 소요 시간이 있을 수 있으나 그건 반복 행동에 붙는 15 구간의 근거(왕복 부담)와 다른 성질이라 10 구간이 맞다. (이 값이 필요한 이유: 보상 행 없이 검증하면 `GrantReward` 가 "Dialogue/Interact 인데 보상 0" 경고를 남겨, 실제 데이터 누락과 구분이 안 되는 노이즈가 생긴다 — §8 조건표 #4.)

**§3-3 에 따라 임시**: 이 행도 §3-1 엔트리와 함께 PIE 검증 후 제거한다. 검증 기간에만 존재하므로 기존 6종 보상 합(80)에 대한 영구 재분배나 재계산은 필요 없다(§7).

## §4 `InteractVerb` 문구 가이드

### 4-1. 기본값 — "조사하기" 유지 권장

코드 기본값 `NSLOCTEXT("SpyInteractable", "DefaultInteractVerb", "조사하기")`(spec §3-1)는 그대로 둔다. 근거:
- `USpyInteractPromptWidget::ShowPrompt(FText InVerb)`(`SpyInteractPromptWidget.cpp:37-41`) 는 `Txt_Verb` 텍스트블록에 동사만 그대로 표시한다 — NPC 경로의 하드코딩 기본값 "대화하기"(`SpyInteractionComponent.cpp:28`)와 같은 위젯·같은 표시 자리(`ESpyUIType::InteractPrompt`)를 공유한다.
- "대화하기"는 2음절 어근("대화") + "하기" = 4음절. "조사하기"도 2음절 어근("조사") + "하기" = 4음절 — **같은 프롬프트 박스에서 나란히 나올 두 동사의 길이가 이미 맞는다.**
- §2 의 "조사형" 체감과 의미가 정확히 일치한다("정보를 캐낸다"가 아니라 "현장을 확인한다").

### 4-2. 향후 오브젝트별 동사 가이드 — 규칙과 예시

**규칙**: 동사는 상호작용의 결과를 예측 가능하게 하고, 이번 범위(1회성 소진)에서는 **"다시 쓸 수 있다"는 오해를 주는 동사를 피한다.** "사용하기"는 반복 사용 가능성을 암시해 1회성 소진과 어긋난다 — 채택하지 않는다. 모든 동사는 `[2음절 어근] + 하기` 패턴(4음절)으로 통일해 "대화하기"와 프롬프트 박스에서 시각적으로 정렬되게 한다.

| 오브젝트 유형 | 권장 동사 | 이유 |
|---|---|---|
| 단서·문서·시체 등 정보성 오브젝트 | **조사하기** | 기본값. 정보 습득이 목적 |
| 레버·스위치·밸브 | **작동하기** | 물리적 조작, 1회성 상태 전환과 자연스럽게 맞음 |
| 컴퓨터·단말기·키패드 | **해킹하기** | 스파이 테마 톤 일치, "조사하기"와 구분되는 기술적 행위임을 표시 |
| 문·게이트·잠금장치 | **개방하기** | "열기"(2음절)보다 "개방하기"(4음절)로 통일해 길이를 맞춘다 |

**향후 여러 오브젝트가 생길 때**: 같은 레벨 구간에 동사가 겹치는 오브젝트를 배치하지 않는다(예: 조사형 오브젝트 2개가 연달아 나오면 "조사하기"만 반복돼 구분이 흐려진다) — 이건 수치가 아니라 레벨 배치 시점의 확인 사항이라 §5 에 실행 지침으로 남긴다.

## §5 오브젝트 배치 가이드 (레벨 디자인)

- **적합한 위치**: 전투/파쿠르처럼 능동적 행동을 요구하는 구간이 아니라, **잠시 멈춰 확인하는 구간**에 배치한다 — 은신 경로 옆 단서, 그래플 타워에 오르기 전 정찰 지점의 단말기 등. mission-system.md §2-4 의 구역 구분(전투/파쿠르/그래플)과 겹치지 않는 **네 번째 성격의 정지 구간**을 만드는 역할로 쓴다.
- **NPC 미션과의 조합**: NPC spec 의 Offer→InProgress→Report 구조 사이에 자연스럽게 끼울 수 있다 — 예: "NPC 가 정보를 요청 → 플레이어가 현장에서 단서 오브젝트를 조사 → 원래 NPC 에게 돌아가 보고". 단, **이번 spec/plan 범위에서 오브젝트 상호작용과 NPC 보고는 서로 다른 진행 신호(`Event.Mission.Interact` vs `Event.Mission.Report`)를 쓰므로, 이런 서사적 연쇄를 실제로 이어 붙이려면 두 미션을 체인에서 연속 배치하는 것 이상의 코드 변경(예: 오브젝트 조사 결과를 NPC 대사 분기에 반영)은 필요 없다** — 순서만 맞추면 된다.
- **오브젝트-NPC 근접 배치 시 우선순위 확인**: spec §5-2 가 "NPC 가 오브젝트보다 우선"으로 이미 확정했다(F키 입력 시 NPC 우선 판정). 따라서 NPC 근처에 조사 오브젝트를 두면 플레이어가 오브젝트에 F를 시도해도 NPC 대화가 먼저 뜬다 — **오브젝트는 NPC 상호작용 반경(§spec 의 `SphereComponent` 반경)과 겹치지 않는 곳에 배치**해야 한다(간격 확보는 사용자가 MCP/에디터 배치 시 직접 조정, 수치는 이번 범위 밖).

## §6 밸런싱/페이싱 확인 — 다인 세션 소진 충돌 (핵심 발견)

### 6-1. 충돌 사실

- 오브젝트 소진(`bConsumed`)은 `COND_None` 으로 **전 플레이어 공용**이다(spec §6 엣지케이스: "같은 방을 도는 다른 플레이어도 소진된 오브젝트와 상호작용하면 안 됨").
- 미션 진행도(`FSpyMissionState`)는 **플레이어별**(PlayerState 컴포넌트, mission-system.md §1-1)이다.
- **결과**: 2인 세션에서 플레이어 A 가 먼저 오브젝트와 상호작용하면 오브젝트는 즉시 소진되고, **플레이어 B 는 그 미션을 영원히 완료할 수 없다** — 오브젝트가 1개뿐이므로 재시도 수단이 없다.

### 6-2. 기존 원칙과의 정합성 — 어긋난다

mission-system.md §4-2 는 "1인·2인 세션 완주를 보장 기준으로 삼는다"를 명시적으로 확정했다. `Interact` 미션을 (검증용이라도) 이 체인에 추가하면 **2인 세션에서 이 기준이 깨진다** — 이건 이 기획서가 완화할 수 있는 문제가 아니라 spec 이 확정한 리플리케이션 방식(`COND_None`)에서 구조적으로 발생한다.

또한 mission-system.md §2-2 의 배치 원칙("유한 자원에 의존하는 미션을 앞에 둔다")도 이 미션에는 **다른 방식으로 적용된다**: 봇(유한 자원)은 다른 미션 수행 중에도 우발적으로 소모되지만(§2-1 경로 A), 오브젝트는 오직 **이 미션을 노리는 의도적 상호작용으로만** 소진된다. 즉 "다른 행동이 자원을 갉아먹는" 경로 A 형 교착이 아니라, **"자원 자체가 그 미션 전용이라 유일한 소비자(첫 상호작용자)만 완료할 수 있다"는 새로운 유형의 제약**이다. 앞으로 배치해도 교착 위험은 없지만(자원이 미션과 1:1 이라 다른 미션에 영향 없음), 다인 완주 보장은 별개로 깨진다. (단, 이번 검증은 1인 세션이므로 관측 대상이 아니다 — §6-3)

### 6-3. 이번 범위에서의 처리 — 시점 분리(임시 검증 vs 정식 편입)

- **이번 임시 검증 엔트리(§3)는 1인 세션 한정이라 이 충돌과 무관하다.** plan Task 6 Step 6 의 PIE 체크리스트도 1인 Standalone 기준이고, §9 의 검증 메트릭(D1~D3)도 전부 1인 세션 대상이다 — 다인 세션 충돌은 이번 검증의 대상이 아니다.
- 다인 세션에서의 이 미션 타입 사용은 **정식 콘텐츠로 편입하는 시점**(plan "완료 후 남는 것"이 분리해 둔 별도의 미래 작업, 이번 plan 범위 밖)에 재검토 대상이다. 그 시점이 오면 **사용자가** 아래 두 방향 중 하나를 선택해야 한다:
  - **(a) 오브젝트 N개 배치** — 동시 접속 가능 인원 수만큼 같은 `MissionEventTag` 오브젝트를 레벨에 배치. 레벨 배치 결정이라 코드 변경 없음.
  - **(b) `bConsumed` 를 플레이어별로 바꾼다** — spec §6 의 레플리케이션 방식 자체를 바꾸는 것이라 spec 수정 필요(코드 변경).
- 지금은 이 결정을 내리지 않는다 — §10-1 에 알려진 제한으로만 남긴다.

## §7 검산

**보상 총합(검증 기간 한정)**: 기존 6종(mission-system.md §3-3) 20+10+10+10+15+15 = 80. 검증 기간 동안 `Interact` 임시 엔트리가 반영되면 일시적으로 80 + 10 = 90 이지만, §3-3 에 따라 PIE 확인 후 이 행을 제거하므로 **영구 총합은 그대로 80** — 재분배·재계산 대상이 아니다.

**레벨 상한 검산 — 인용 출처 정정**: 누적 XP 120 = Lv4(최대 레벨) 도달이 "index 11(마지막 Dialogue) 완료" 시점이라는 사실의 근거는 mission-system.md §4-1 이 아니다 — 그 문서는 기존 6종 미션(index 0~5)의 프레임 단위 검산만 다뤄서 index 11 자체가 존재하지 않는다. 이 사실은 **NPC spec(`2026-08-01-npc-mission-dialogue-design.md`) §4-8 의 12행 체인 예시 데이터에서 직접 도출**된다. 또한 그 NPC spec §4-9 는 "mission-system.md §4 의 프레임 단위 검산표는 참고용으로 격하한다"고 명시했으므로, mission-system.md §4-1 을 프레임 단위 사실의 근거로 직접 인용하는 것 자체가 부적절하다 — 이전 판의 인용을 이렇게 정정한다. (같은 이유로 §3-3 의 "이 불변식을 유지"라는 표현도 "NPC spec §4-9 가 명시적으로 보존한다고 확인한 불변식(보상합·최소 킬·레벨 임계값)에서 재도출"로 읽는다.)

검증 기간 동안 `Interact`(임시 `MissionId` 13) 완료 보상 10 을 더하면 누적 130 이지만 Lv4 가 상한이므로 **초과분 10 은 레벨 판정에 영향 없음**(experience-level.md §7). 이 값도 검증 기간에만 발생하고, 엔트리 제거 후에는 원래 체인(`MissionId` 1~12)만 남으므로 **영구 레벨 밸런스에는 애초에 영향이 없다**.

**필요 조건 검산(단일 실패점)**: 이 미션이 0 에 머무는 경우는 정확히 두 가지로 특정된다 — (1) `MissionEventTag`(오브젝트) ≠ `MatchTag`(미션 엔트리) 불일치, (2) `DA_SpyMissionConfig` 배열에 엔트리 자체가 없거나 순서가 어긋남. mission-system.md §6-5 형식을 따라 §8 에 조건표로 남긴다.

## §11 이번 범위에서 명시 제외

spec §1 의 비목표를 그대로 따른다. 이 기획서는 아래에 대해 어떤 수치·배치도 제안하지 않는다.

| 항목 | 사유 |
|---|---|
| DevMap 실제 배치(좌표·오브젝트 개수) | spec 비목표 — 사용자가 MCP/에디터에서 직접 수행 |
| 여러 오브젝트 순차 상호작용, 아이템 인벤토리 연동 | spec 비목표 |
| 오브젝트별 고유 연출(VFX/사운드) | spec 비목표 — §10-2 에 제한으로만 명시 |
| 재사용 가능한(반복 상호작용) 오브젝트 | spec 비목표 — 이번 타입은 전부 1회성 |
| `bConsumed` 리플리케이션 방식 변경(§6-3 (b)) | spec 이 확정한 기술 설계 — 이 기획서는 재론하지 않는다 |
| `FSpyMissionRow`/`FSpyMissionRewardRow` 필드 추가·변경 | plan 확정 스키마 — 값만 채운다(§3) |
| 정식 콘텐츠용 다수 `Interact` 미션 설계 | 이번은 검증용 1건. 다수 설계는 §7-1 트리거 발동 후 별도 기획 |
| 2인(다인) 세션에서 §6-1 소진 충돌 실측 (구 §9 D4) | **권장수정 1 반영**: 이번 임시 검증은 1인 세션 한정(§6-3), plan 에도 2인 PIE 절차가 없다. 다인 검증은 정식 콘텐츠 편입 시점(§6-3 (a)/(b) 결정 이후)에 별도로 수행한다 |
