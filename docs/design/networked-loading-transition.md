# 네트워크 로딩 전환 — 값·UX 기획

> **이 문서의 범위**: 승인된 구조 안에 들어갈 **도메인 값** — `ConnectTimeoutSeconds` · 접속 단계 바 creep 감각 · 에러 UX 문구/색/배치 · `ServerAddress` 개발 기본값 · 오프라인 폴백 유지 의견 — 의 확정과 근거.
> 구조(`ClientTravel` 전환, GameInstance 타이머, 접속 모드 로컬 스트리밍 생략, 순수 함수 4종, 도착 판정 강화)는 [spec](../superpowers/specs/2026-07-23-networked-loading-transition-design.md) 과 [plan](../superpowers/plans/2026-07-23-networked-loading-transition.md)(Task 14~20)이 확정했다. **이 문서는 그것을 다시 제안하지 않고 뒤집지도 않는다.**
> **선행 값의 SoT**: [`loading-scene.md`](loading-scene.md) — `MinDisplaySeconds = 2.5` · `AssetPhaseWeight = 0.9` · 색/서체/레이아웃 · 측정치(T1 2.725s / T2 0.308s / T3 0.147s). 이 문서는 그 값들과 **정합**을 유지하며, 하나도 바꾸지 않는다.

---

- **목표** — 클라이언트가 로딩 화면을 거쳐 데디케이티드 서버에 접속·진입하는 전환의 **시간 값과 접속 단계 체감**을, 그리고 접속 실패 시 **에러 화면의 문구·톤·배치**를 근거와 함께 확정한다.
- **검증 가설** — 접속 단계에서 **바가 멈춰 보이지 않고**(이번에 고치는 증상이 정확히 "100% 고정"이다) 도착까지 계속 움직이며, 접속 실패 시 사용자가 상황을 읽고 재시도로 복구할 수 있는가.
- **현재 단계 범위 적합성** — `project.md` 의 `stage`/`stage_goal` 및 컨셉서 §1 세부 톤·§2·§4·§5 는 여전히 `(사용자 확정 대기)`. 단계 부합을 단정하지 않고 **사용자 승인 완료 spec(2026-07-23-networked-loading-transition-design.md)의 목적·§9 범위 밖 목록을 범위 경계로 삼는다.** spec §9 범위 밖(메인 메뉴·서버 브라우저·매치메이킹·주소 입력 UI·Seamless Travel·MoviePlayer)은 §8 에 명시 제외로 남긴다. 에러 UI 의 색·문구 톤은 `loading-scene.md` §5 와 동일하게 **"차갑고 절제된 첩보 계측기" 톤 가정** 위의 작업값이며, 컨셉서 §1 확정 시 §4-4 절차로 갱신한다.
- **핵심 메커니즘** — 전환 시점(프리로드 완료 + `MinDisplaySeconds`)에 바는 프리로드 지점 `0.9`(=`AssetPhaseWeight`)에 있다. 여기서 `ClientTravel` 을 개시하고, GameInstance 타이머가 바를 `0.9 → 0.995`(상한 비율 0.95)로 **`ConnectTimeoutSeconds` 에 걸쳐** 기어오르게 한다. `1.0` 은 실제 도착(`PostLoadMapWithWorld`, 비-로딩 월드) 시에만 찍는다. **creep pacing 을 timeout 과 같게 묶는 것**이 이 설계의 핵심이다(§3).

## §2 `ConnectTimeoutSeconds` — 최종값 **15초** (plan 기본값 유지 확정)

### 2-1. 결정

| 항목 | 값 |
|---|---|
| `USpyLoadingConfig::ConnectTimeoutSeconds` | **15** |
| plan 기본값 | `15.f` (→ 이 기획서가 값 근거를 확정하며 유지) |
| 의미 | `ClientTravel` 개시 후 이 시간 안에 도착(`PostLoadMapWithWorld`)이 없으면 **"서버가 느린 것"이 아니라 "죽은 것"으로 간주**하고 실패 처리 |

### 2-2. 근거 ① — 이 프로젝트에서 접속 시간은 **맵 다운로드가 아니라 핸드셰이크+합류**로 결정된다

타임아웃은 "정상 접속의 최대 소요"에 안전 배수를 곱해 잡는다. 그 최대 소요를 구성 요소로 분해한다.

**먼저, 이 프로젝트에서 클라는 서버로부터 185MB 맵을 다운로드하지 않는다.** DevMap 은 쿠킹된 로컬 패키지로 클라에 이미 있고, 1단계 프리로드가 그 참조 폐포(`loading-scene.md` §3-3: 겹침 185.4MB)를 **이미 캐시에 올려 둔** 상태다. 따라서 `ClientTravel` 의 맵 로드는 "서버에서 내려받기"가 아니라 **로컬 캐시 히트**(측정 `T3 = 0.147s`)다. **맵 규모는 타임아웃을 좌우하지 않는다** — 이것이 task 가 "측정된 DevMap 규모를 고려하라"고 물은 지점의 답이다.

남는 구성 요소:

| 구간 | 정상 소요(추정) | 근거의 성격 |
|---|---|---|
| (a) TCP 연결 + UE 핸드셰이크(challenge/response/join, 수 왕복) | **~0.5–2s** | 원격 서버 RTT 200ms × 수 왕복. 로컬은 프레임 단위 |
| (b) 서버 측 `PostLogin` + 폰 스폰 + 초기 액터 채널 리플리케이션 | **~1–3s** | 서버 부하·상주 액터 수에 의존. 추정 |
| (c) 클라 로컬 맵 로드(캐시 히트) | **~0.15s** | 측정 `T3` |
| **정상 최대 소요 소계** | **~2–5s** | (a)+(b)+(c), 세 값 중 둘이 추정 |

**타임아웃 = 정상 최대 소요(~5s)의 약 3배 = 15s.** 3배 배수의 뜻: 정상 접속이 이 시간을 넘기려면 (a)+(b)+(c)가 셋 다 최악을 동시에 3배 초과해야 하며, 그건 "느린 서버"가 아니라 "응답 없는 서버"다. 즉 15s 는 **"느림"과 "죽음"을 가르는 임계값**으로 기능한다.

### 2-3. 근거 ② — 오탐(정상을 실패로) 비용 > 지연(죽은 서버에 매달림) 비용

- **오탐**(정상 접속을 실패로 판정): 사용자가 곧 붙을 서버를 "실패"로 보고 재시도를 누르면, `ClientTravel` 이 재개시되며 진행 중이던 접속을 버린다 — 접속이 **더 늦어진다**. 회복 불가에 가까운 나쁜 경험.
- **지연**(죽은 서버를 15s 매달림): 사용자가 15s 기다린 뒤 에러+재시도를 본다. 지루하지만 **명확히 회복 가능**.
- 비대칭이 크므로 **경계를 지연 쪽으로** 둔다 → 넉넉한 15s. 로컬 개발에서는 후술처럼 대부분의 실패가 타임아웃 전에 즉시 감지되므로(§2-4) 15s 지연이 실제로 발생하는 경우는 드물다.

### 2-4. 로컬 개발에서 15s 지연은 거의 발생하지 않는다

가장 흔한 실패인 **"서버 미실행 + localhost"** 는 OS 가 TCP 연결을 **즉시 거부**(`ECONNREFUSED`)하므로 `OnNetworkFailure` 델리게이트가 **1초 안에** 발화한다 — 타임아웃(15s)이 아니라 즉시 에러다. 15s 타임아웃이 실제로 지배하는 경우는 **거부도 응답도 없이 매달리는** 상황(원격 서버 다운/방화벽 드롭/잘못된 원격 주소)뿐이고, 이는 localhost 중심 개발에서 재현되지 않는다. → **15s 값의 적정성은 로컬 테스트로 판정되지 않는다**(§7-1).

### 2-5. 대안 비교

| 안 | 값 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | 8s | 죽은 원격 서버를 빨리 포기 | 정상 최대 소요(~5s)와 마진이 1.6배뿐 — 부하 큰 서버 접속을 오탐할 위험 | 기각 |
| **B** | **15s** | 정상 최대의 ~3배 마진, 오탐 실질 차단 | 죽은 원격 서버에 최대 15s 매달림(단 §2-4로 드묾) | **채택** |
| C | 30s | 오탐 마진 최대 | 죽은 서버 대기 30s — §2-3 지연 비용이 과함. creep pacing(=timeout, §3)이 30s로 늘어져 바가 지나치게 느리게 김 | 기각 |

### 2-6. 재조정 메트릭 — **M-Net-1**

원격/실서버 환경이 생기면 정상 접속 실측 `T_connect`(접속 개시 → 도착 로그 간격, §7-2)를 5회 수집한다.
- `max(T_connect) × 3` 을 0.05초 아닌 **1초 단위**로 반올림해 재설정한다(예: 실측 최대 6s → 18s).
- **하한 `8s`**(§2-5 안 A 근거), **상한 `30s`**(안 C 근거) 밖으로는 나가지 않는다.
- `ConnectTimeoutSeconds` 는 **반드시 `> 0`** 이어야 한다 — `0` 이면 `HasConnectTimedOut` 이 무제한이 되고 creep pacing 도 0 이 되어 §3 의 creep 이 붕괴한다(즉시 상한 고정).

## §3 접속 단계 바 creep — **pacing = timeout(15s), 상한 비율 0.95 유지**

### 3-1. 결정

접속 개시 시 바는 프리로드 지점 `0.9` 에 있다. 여기서 도착까지 **`ConnectTimeoutSeconds`(15s)에 걸쳐** `0.9 → 0.995` 로 기어오른다. `1.0` 은 도착 시에만.

```
display(t) = PreloadWeight + (1 − PreloadWeight) × min(t / pacing, 1) × ConnectDisplayCap
           = 0.9 + 0.1 × min(t / 15, 1) × 0.95
```

| 시각 t | display | 퍼센트 텍스트(`RoundToInt`) |
|---|---|---|
| 0s (접속 개시) | 0.900 | `090%` |
| 7.5s (pacing 절반) | 0.9475 | `095%` |
| 14.9s | 0.9944 | `099%` |
| **15.0s (= pacing = timeout)** | 0.995 | `100%` — 그러나 **같은 틱에 타임아웃 발화 → 바·퍼센트 숨김**(§3-3) |
| 도착(성공, 아무 때나) | **1.000** | `100%` |

### 3-2. 근거 — pacing 을 timeout 과 같게 묶는 이유 (핵심)

creep pacing 은 "바가 상한(0.995)에 닿는 데 걸리는 시간"이다. 이 값은 **사용자가 접속을 기다릴 수 있는 최대 시간, 즉 timeout 과 같아야 한다.**

- **pacing < timeout 이면 "얼어붙은 꼬리"가 되살아난다.** 예로 pacing 을 3s 로 짧게 잡으면, 바는 3s 에 0.995 에 닿은 뒤 **timeout(15s)까지 남은 12s 동안 0.995 에 정지**한다. 이는 이번 기능이 고치려는 "100% 근처 고정" 증상을 **접속 단계에 그대로 재현**하는 것이다.
- **pacing = timeout 이면** 바는 타임아웃 순간에야 상한에 닿으므로, **정지 구간 없이 대기 전 구간에서 계속 움직인다.** 도착이 그 전에 오면 1.0 으로 마무리, 안 오면 상한에 닿는 순간이 곧 에러 순간이다.

pacing=timeout 은 임의 선택이 아니라 위 두 손실(정지 재현 vs 대기 내내 움직임)을 저울에 올린 결정이며, plan Task 17 Step 4 가 `ConnectPacingSeconds` 에 `ConnectTimeoutSeconds` 를 넘기는 것이 이 결정과 일치한다 — 유지한다. 성공 경로에서도 도착 스냅은 최대 ~9.4%p 로 `loading-scene.md` §4-3 의 계단 임계치(15%p) 아래라 매끄럽다(§3-4 교차 참조).

### 3-3. 상한 비율 `0.95` — **유지**(실패 시 바·퍼센트 숨김으로 100% 표기 자체가 안 보임)

**우려**: 상한 display = `0.9 + 0.1×0.95 = 0.995`. 그런데 `RoundToInt(0.995 × 100) = RoundToInt(99.5) = 100`(UE `RoundToInt = FloorToInt(F+0.5)`)이므로, 상한에서 **퍼센트 텍스트가 "100%"** 를 찍는다. 그리고 타임아웃 시각(t=15.0s)에 타이머가 멈추면 `DisplayedProgress` 는 0.995 에 **동결**되므로, 이 "100%" 표기는 한 프레임이 아니라 **에러 상태 내내 지속**될 수 있다 — "실패했는데 100%"라는, 이번 기능이 없애려는 바로 그 모순이다.

**해소 — 사용자 결정: 실패 시 바·퍼센트를 아예 숨긴다(§4-3).** `HandleConnectionFailed` 에서 `LoadingBar`·`PercentText` 를 `Collapsed` 로 두므로, 실패 화면에는 **바도 퍼센트도 존재하지 않는다.** 따라서 0.995 가 100% 로 반올림되든 말든 **화면에 표시되는 100% 자체가 없다.** 재시도 시 `OnRetryClicked` 가 둘을 복원하고, `RetryConnect` 가 `DisplayedProgress` 를 프리로드 지점(0.9)으로 되돌려 **재시도 바가 100% 로 남지 않게** 한다.

**결정: `ConnectDisplayCap = 0.95` 유지.** cap 을 `0.90`(→상한 0.99, `099%`)으로 낮추는 것은 "표시되는 100% 를 없애는" 조치인데, **숨김 처리가 이미 그 100% 를 화면에서 제거**했으므로 cap 을 건드릴 이유가 사라진다. 낮추려면 plan 코드 상수 1개 + Task 15 테스트 기대값 3개(`0.9475→0.945`, `0.995→0.99` 2곳)를 함께 바꿔야 하는데, 얻는 게 없다. **churn 0, 값 유지.**

> **단, `ConnectTimeoutSeconds > 0` 는 강제 조건이다**(§2-6). `0` 이면 pacing=0 → creep 이 즉시 상한(0.995)으로 점프해 도착까지 **거기서 정지**한다. 이것이야말로 상한을 낮춰도 못 고치는 진짜 "얼어붙은 바"다. Config 가이드로 §9-1 에 명시한다.

### 3-4. localhost 에서 creep 은 거의 안 보인다 (검수 주의)

기본 주소 `127.0.0.1:7777` 는 **1초 안에** 접속되므로, 바는 0.9 에 잠깐 머물다 도착 시 1.0 으로 **약 9.4%p 스냅**한다(0.906→1.0). 이 스냅은 `loading-scene.md` §4-3 의 보간 전환 임계치(단일 프레임 **15%p**)의 절반이라 **보간 없음 결정과 정합**한다 — 계단으로 문제되지 않는다. 대신 **`0.9→0.995` creep 자체는 로컬에서 거의 관찰되지 않는다.** creep 이 눈에 보이는 것은 느린/원격/매달리는 접속뿐이므로, **15s pacing 의 적정성은 로컬 테스트가 아니라 §3-2 의 논증으로 확정된다**(§7-1). "로컬에서 creep 이 안 보인다"를 버그로 오해해 pacing 을 건드리지 말 것.

spec §5-4 는 실패 시 "바·퍼센트를 흐리게/멈추고 에러를 표시"하라고 했으나, **흐림(부분 불투명)으로는 §3-3 의 "실패했는데 100%" 모순이 남는다** — 타임아웃 시 퍼센트가 0.995(→표기 `100%`)에 동결되고, 흐릿하게라도 그 "100%"가 화면에 계속 보이기 때문이다. **사용자가 "흐림이 아니라 완전 숨김"으로 결정했다.**

- **확정**: `HandleConnectionFailed` 에서 `LoadingBar`·`PercentText` 를 **`Collapsed`** 로 숨긴다. 실패 화면에는 바도 퍼센트도 없고 **에러 메시지 + 재시도 버튼만** 남는다 — "거의 다 참 + 연결 실패" 모순이 원천 제거된다.
- **복원**: `OnRetryClicked` 에서 둘을 다시 보이게 하고, `RetryConnect` 가 `DisplayedProgress` 를 프리로드 지점(0.9)으로 되돌려 **재시도 시 바가 100% 로 남지 않는다.**
- plan Task 18 은 이 결정으로 이미 갱신됐다(`Collapsed`/복원). 이 절은 그 연출 값(완전 숨김·프리로드 리셋 0.9)의 근거를 확정한다.

### 4-4. z-order — 에러 UI 는 **맨 위**(배경 규칙의 역방향)

`loading-scene.md` §5-2 는 배경 `Border` 를 캔버스 자식 목록 **맨 앞**(뒤에 그려짐)에 둔다. 에러 UI 는 그 반대다 — **`ErrorText`·`RetryButton` 을 자식 목록 맨 뒤**(가장 위에 그려짐)에 둬 바/퍼센트 위에 뜨게 한다. UMG 는 "나중 자식이 위에" 규칙이므로 최종 배치 순서:

**① 배경 `Border` → ② `LoadingBar` → ③ `PercentText` → ④ `ErrorText` → ⑤ `RetryButton`**

plan Task 19 Step 2 가 위젯을 손으로 배치하므로 이 순서를 §9-2 에 못박는다. 순서가 어긋나 에러 UI 가 바 레이어 뒤로 가면 실패 화면에서 안 보인다.

## §5 `ServerAddress` 개발 기본값 — **`127.0.0.1:7777`** (유지 확정)

### 5-1. 결정

`DA_SpyLoadingConfig.ServerAddress = "127.0.0.1:7777"` (plan Task 19 Step 1 값 유지 확정).

### 5-2. 근거

- **포트 7777** — UE 기본 서버 포트(`?listen` 기본값, `-port=7777`)다. plan Task 20 Step 1 의 서버 실행 예(`-port=7777`)와 일치하고, 에디터 "Run Dedicated Server" 모드도 이 포트로 로컬 서버를 띄운다 → 별도 설정 없이 **기본 검증 경로가 곧바로 맞물린다.**
- **비어 있지 않은 값을 기본으로** — 기본 경로가 **접속 모드**여야 이번에 고친 실제 코드 경로(`ClientTravel` 접속)를 항상 탄다. 오프라인은 §6 처럼 필드를 비우는 **명시적 옵트인**으로 남긴다.

### 5-3. 알려진 개발 편의 트레이드오프 (은폐하지 않음)

기본값이 접속 모드라, `ServerAddress` 를 채운 채 **로컬 서버 없이 Standalone Play** 하면 접속 실패(→에러+재시도)가 뜬다. 이는 버그가 아니라 spec 모델의 정상 동작(클라는 부팅 후 서버에 접속)이다. 혼자 게임플레이만 반복하려는 개발자는 §6 의 오프라인 폴백을 옵트인한다. 정식 검증 경로(에디터 "Run Dedicated Server")는 로컬 7777 서버를 함께 띄우므로 이 마찰이 없다. **트레이드오프를 감수하고 기본=접속을 유지**하는 이유는 §5-2(실경로 상시 검증)다.

### 6-1. 의견

plan 이 남긴 오프라인 폴백(`ServerAddress` 비면 `NM_Standalone` 에서 `OpenLevel(GameplayMap)`)을 **유지한다.**

### 6-2. 근거

- **현재 이 프로젝트에는 독립 데디서버 실행 파일이 없다** — plan Task 20 Step 0 이 확인한 사실: `SkillProjectServer.Target.cs` 부재로 `SkillProjectServer.exe` 를 빌드할 수 없다. 따라서 지금 마찰 없는 개발 경로는 **(a) 에디터 "Run Dedicated Server"** 와 **(b) 오프라인 폴백 Standalone** 둘뿐이다. 폴백을 없애면 게임플레이 반복마다 (a)의 서버+클라 분리 실행을 강제하게 되어 iteration 이 느려진다.

### 6-3. 결론

값/플래그 수준의 권장: **폴백 유지 + 기본 `ServerAddress` 비우지 않음**(§5). 오프라인은 "필드 한 번 비우기"로 켜는 개발용 스위치로 둔다.

## §7 검수 계획 · 한계

### 7-1. 로컬(localhost/에디터 데디서버)에서 판단하면 안 되는 것

> **다음은 localhost 로 검증되지 않는다 — 논증으로 확정된 값이다:**
> - **`ConnectTimeoutSeconds`(15s)의 적정성** — localhost 실패는 대부분 즉시 거부(§2-4)라 타임아웃이 지배하지 않는다. 15s 는 §2 의 분해·배수 논증으로 정해졌다.
> - **`0.9→0.995` creep 감각** — localhost 접속은 <1s 라 creep 이 거의 안 보이고 도착 스냅만 보인다(§3-4). creep pacing 은 §3-2 의 "얼어붙은 꼬리 방지" 논증으로 정해졌다. **로컬에서 안 보인다고 pacing 을 건드리지 말 것.**
>
> **localhost/에디터 데디서버로 검증 가능한 것**: 검은 화면·바 100% 고정이 **사라졌는지**(핵심 회귀), 접속 실패 시 에러 문구·색·재시도 버튼이 §4 대로 뜨는지, 재시도가 동작하는지, 오프라인 폴백이 도는지.

### 7-2. 측정 항목

| ID | 측정 | 방법 | 결정 대상 |
|---|---|---|---|
| **M-Net-1** | 정상 접속 소요 `T_connect`(접속 개시 → 도착 로그 간격) | 원격/실서버 확보 시 5회 로그 타임스탬프 (`서버 접속 개시` → `도착 — 로딩 UI 종료`) | §2-6 (`ConnectTimeoutSeconds` 재조정) |
