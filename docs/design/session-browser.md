# OSS 세션 브라우저 (방 목록) — 값 · 레이아웃 · 문구 기획

> **이 문서의 범위**: 이미 확정된 세션 브라우저 구조 안에 들어갈 **도메인 값** — `USKOnlineSettings` 수치 · 방 목록 화면 레이아웃/색/서체 · 행 컬럼 구성 · 화면 문구 — 의 확정과 그 근거.
> 클래스 구조 · 플러그인 경계 · API 시그니처 · 델리게이트 · BindWidget 이름 · 흐름은 [spec](../superpowers/specs/2026-07-28-oss-session-browser-design.md) 과 [plan](../superpowers/plans/2026-07-28-oss-session-browser.md) 이 이미 확정했다. **이 문서는 그것을 다시 제안하지 않고 뒤집지도 않는다.**
> **선행 값의 SoT**: [`loading-scene.md`](loading-scene.md) (§5 색·서체·레이아웃 좌표계) · [`networked-loading-transition.md`](networked-loading-transition.md) (§4 에러 UX 톤·문구 규약, `RetryButton` 스타일). 이 문서는 그 값들과 **정합**을 유지하며 하나도 바꾸지 않는다.

---

- **목표** — 로딩 완료 후 뜨는 방 목록 화면의 **세션 수치(인원·검색 수·방 이름)** 와 **화면 값(레이아웃·색·서체·문구)** 을 근거와 함께 확정해, 목업 게이트(plan Task 9 Step 1)와 구현이 값 때문에 멈추지 않게 한다.
- **검증 가설** — 로딩이 끝난 플레이어가 **방 목록 화면을 보고**(= 화면이 실제로 앞에 그려지고 클릭이 먹고), 방을 만들거나 고르는 두 갈래를 헤매지 않고 고를 수 있으며, 결과가 없거나 실패했을 때 무슨 일이 일어났는지 문구로 읽히는가.
- **현재 단계 범위 적합성** — `project.md` 의 `stage`/`stage_goal` 은 여전히 **(사용자 확정 대기)** 이고 컨셉서 §2·§4·§5 도 미확정이다. 따라서 단계 부합을 단정하지 않고, **사용자 승인이 완료된 spec(2026-07-28-oss-session-browser-design.md)의 목적과 §9 명시 제외 목록을 이 기획서의 범위 경계로 삼는다.**
  - spec §9 의 **"인원 꽉 참"** 제외는 *꽉 찼을 때의 게임플레이 처리*(대기열·강퇴·방장 위임·재입장)를 뜻한다. 반면 **목록 행의 참가 버튼 비활성 표시**는 plan Task 6 Step 2 가 이미 구현하는 **표시 규칙**이므로 이 기획서가 §4-5 에서 그 시각 값을 확정한다 — 범위 내다.
  - 색·문구 톤은 `loading-scene.md` §5 와 동일하게 **"차갑고 절제된 첩보 계측기" 톤 가정** 위의 작업값이다. 컨셉서 §1 세부 톤 확정 시 §7-2 절차로 갱신한다.
- **핵심 메커니즘** — 화면은 **좌 로고(560×360) / 우 방 목록(1040×520) 2단**이다(§4-2, 사용자 승인 목업). 목록은 **ScrollBox 6행 가시**(pitch 80px)로 최대 `MaxSearchResults`(20)행을 담고, 행은 `방 이름 / 인원 / 핑 / 참가` 4열이다. 행 간격 8px 은 슬롯 패딩이 아니라 **행 위젯 안에 내장**돼 런타임 `AddChild` 경로와 무관하게 성립한다(§4-3). 상태 통지는 `StatusText` **한 줄**이 진행·빈 목록·에러를 모두 맡고, 표시 문구는 **지금 진행 중인 op** 를 따른다(§5-2-1). 이 화면은 **persistent 로딩 UI(ZOrder 100)보다 위(200)** 에 그려진다(§3 — 결정 완료).

## §2 `USKOnlineSettings` 수치

### 2-1. `MaxPlayers` — **4** (plan 기본값 유지 확정)

#### 2-1-1. 결정

| 항목 | 값 |
|---|---|
| `USKOnlineSettings::MaxPlayers` | **4** |
| plan 기본값 | `4` (→ 이 기획서가 근거를 확정하며 **유지**) |
| 의미 | 세션의 `NumPublicConnections`. 호스트를 **포함**한 방 정원 |

#### 2-1-2. 근거 ① — 스폰 지점은 이 값을 유도하지 못한다 (실측)

task 는 "`DevMap` 의 PlayerStart 수와 정합을 맞출 것" 을 요구했다. 실측 결과 **`DevMap` 의 PlayerStart 는 1개**(허브 `(0, 0, 92)`, §1-2)다.

**1개는 2 이상 어떤 정원과도 정합하지 않는다.** 즉 "PlayerStart 수 = MaxPlayers" 라는 정합 규칙을 적용하면 `MaxPlayers = 1` 이 되는데, 그러면 **아무도 조인할 수 없어 이번 기능 자체가 성립하지 않는다**(그리고 plan Task 2 의 `ClampMin = 2` 와 테스트 `MaxPlayers >= 2` 에도 걸린다). 따라서 이 값은 스폰 지점에서 유도할 수 없고, **다른 근거로 정한 뒤 불일치를 기록하는 것**이 맞다.

**불일치의 실제 결과 — 크래시나 스폰 실패는 아닐 것으로 본다** (근거의 성격: **엔진 기본 동작 가정 — M-SB-4 로 확인**). `AGameModeBase::SpawnDefaultPawnAtTransform` 이 스폰 충돌 처리를 `AdjustIfPossibleButAlwaysSpawn` 으로 지정한다는 전제이며, 그렇다면 같은 PlayerStart 에 2명 이상이 스폰돼도 캡슐이 밀려나며 **항상 스폰된다**. 예상되는 증상은 "게임 시작 순간 캐릭터들이 같은 자리에서 서로 밀려남" 이고, DevMap 은 시연·검증용 맵이므로 이번 사이클에서 감수 가능하다. 은폐하지 않고 §6 M-SB-4 로 관측 대상에 올린다.

#### 2-1-3. 근거 ② — 값을 낮춰도 이번 사이클에 새로 검증되는 것이 없다

"`MaxPlayers = 2` 로 낮추면 2인 테스트에서 꽉 찬 방(`2 / 2`)을 만들 수 있다" 는 유혹이 있으나 **성립하지 않는다**. A가 호스트로 인게임에 들어가고 B가 조인해 인게임에 들어가면 **브라우저 화면에 남아 그 꽉 찬 행을 볼 사람이 없다.** 꽉 찬 방의 비활성 행을 눈으로 확인하려면 `MaxPlayers + 1` 개 인스턴스가 필요하다 — 2 로 낮춰도 3개가 필요하고, 4 면 5개가 필요하다. **이번 사이클(2 인스턴스)에서는 어느 값이든 이 UX 가 검증되지 않는다.**

검증 이득이 0 이므로 남는 기준은 **변경 비용**뿐이다:

- plan Task 10 Step 2 의 기대 표기 `1 / 4` 를 건드리지 않는다(문서 delta 0).
- 나중에 조정하는 비용이 `DefaultGame.ini` 또는 프로젝트 설정 **1줄**이다(`USKOnlineSettings` 는 `config = Game, defaultconfig`). 지금 확정해 얻는 것보다 나중에 바꾸는 비용이 훨씬 싸므로, 현 단계에서 **가장 적게 흔드는 값**을 고른다.

#### 2-1-4. 대안 비교

| 안 | 값 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | 2 | 스폰 겹침이 최소(2인). "꽉 참" 상태를 3 인스턴스로 만들 수 있음 | 이번 사이클 검증 이득 0(§2-1-3). plan Task 10 Step 2 기대값 `1 / 4` delta 발생. 3인 데모 시 ini 재조정 필요 | 기각 |
| **B** | **4** | plan·테스트·검증 절차 delta 0. 4인까지 데모 가능. 조정 비용 1줄 | PlayerStart 1개와 불일치 — 2인 이상 동일 지점 겹침 스폰(밀림) | **채택** |
| C | 8 | 인원 여유 최대 | 겹침 스폰이 8인으로 악화. LAN 검증 환경(2 인스턴스)과의 거리가 더 멀어짐. 근거 없는 상향 | 기각 |

#### 2-1-5. 재조정 메트릭 — **M-SB-4**

- **DevMap 허브의 PlayerStart 가 3개 이상으로 늘어나면** `MaxPlayers` 를 `min(PlayerStart 수, 8)` 로 재검토한다.
- **2인 조인 검증(Task 10 Step 2)에서 캐릭터가 서로 겹쳐 보이거나 밀려나는 것이 플레이에 방해가 되면**, §7-2 의 "허브 PlayerStart 추가" 를 다음 단계로 승격한다.
- 컨셉서 §2 코어 루프가 확정돼 목표 동시 접속 인원이 정해지면 **그 값이 이 값을 대체한다** — 그때는 이 절의 근거(검증 가능성)가 아니라 게임 디자인이 상위 근거다.

### 2-2. `MaxSearchResults` — **20** (plan 기본값 유지 확정)

| 항목 | 값 |
|---|---|
| `USKOnlineSettings::MaxSearchResults` | **20** |
| plan 기본값 | `20` (→ **유지**) |

**근거**

- **목록 UI 가 20행을 감당한다.** §4-1 이 패널을 `ScrollBox` 로 확정했으므로 20행(콘텐츠 높이 `20 × 80 = 1600px`)이 와도 스크롤로 전부 접근된다. 상한을 낮춰야 할 UI 측 제약이 없다.
- **검색 체감 시간은 결과 수가 아니라 백엔드 대기가 지배한다.** OSS Null 의 LAN 검색은 브로드캐스트 응답을 정해진 시간 동안 수집하므로, 결과가 1건이든 20건이든 **완료까지 걸리는 시간이 거의 같다.** 상한을 10 으로 낮춰도 사용자가 체감하는 대기는 줄지 않는다 — 낮출 이득이 없다.
- **하한 쪽 위험은 실재한다.** 상한이 너무 낮으면(예: 5) LAN 에 방이 여러 개일 때 **내 방이 잘려 안 보이는데 사용자는 그 사실을 알 수 없다**(목록에 "더 있음" 표시가 없다). 20 은 LAN 개발 환경에서 사실상 도달하지 않는 여유값이다.

**대안 비교**

| 안 | 값 | 장점 | 단점 | 판정 |

| A | 10 | 목록 최대 길이 절반 | 검색 시간 이득 없음(위). 잘림 위험만 커짐 | 기각 |

### 2-3. `DefaultRoomNameFormat` — **`"{0}의 방"`**, 폴백 **`"Player"`** (plan 기본값 유지 확정)

**근거**

- **옵션 입력 화면이 없으므로(D5) 방 이름은 자동 생성이 유일한 경로다.** 그 이름은 목록에서 **호스트를 지목하는 기능**을 해야 한다. `"{0}의 방"` 은 소유자를 문장 안에 넣어 그 역할을 직접 수행한다.

### 2-4. `bAllowJoinInProgress` — **`true`** (plan 기본값 유지 확정)

task 목록에는 없지만 **§5 흐름 전체가 이 값에 의존**하므로 검토했다는 사실을 남긴다.

- 호스트는 `HostAndEnter()` 로 **방을 만든 직후 곧바로 인게임 맵(`?listen`)으로 트래블**한다(plan Task 5 Step 6·7). 즉 조인하는 사람이 목록을 보고 클릭하는 시점에 **방은 이미 "게임 진행 중"** 이다.
- 따라서 `bAllowJoinInProgress = false` 면 **모든 조인이 거부되어 이번 기능이 성립하지 않는다.** 로비 맵이 없는 현 구조(spec §9 "로비 맵" 제외)에서 `true` 는 선택이 아니라 **전제**다.
- spec §9 의 "게임 중 재입장" 제외와 혼동하지 않는다 — 그것은 *끊긴 플레이어가 다시 들어오는* 기능이고, 이 플래그는 *진행 중인 세션에 신규 참가를 허용*하는 세션 속성이다.

### 2-5. `SearchTimeoutSeconds` — **본 기획서 범위 외** (명시 제외)

spec §4-4 표와 §8 은 `SearchTimeoutSeconds` 를 game-designer 확정 대상으로 올렸으나, **plan Task 2 의 `USKOnlineSettings` 필드 목록에 이 필드가 없다**(`bIsLanMatch` / `bUsesPresence` / `bUseLobbiesIfAvailable` / `bShouldAdvertise` / `bAllowJoinInProgress` / `MaxPlayers` / `MaxSearchResults` / `DefaultRoomNameFormat` 8개뿐이며, plan Task 4 의 `FindSessions` 도 `FOnlineSessionSearch::TimeoutInSeconds` 를 건드리지 않는다).

**필드를 새로 만드는 것은 구조 결정이고 구조는 plan 이 단일 진실**이므로, 이 기획서는 값을 만들어 넣지 않는다. **스펙 §8 의 `SearchTimeoutSeconds` 항목은 본 기획서 범위 외로 명시 제외**하며, 필요하다고 판단되면 plan 에 필드를 추가하는 별도 결정(§7-2 다음 단계 제안)으로 처리한다. 현재는 엔진 기본 타임아웃으로 동작한다.

## §3 렌더 순서 — 방 목록은 로딩 UI **위**에 그려진다 (**결정 완료**)

> **상태: 해소됨.** 이 절이 제기한 블로커에 대해 **사용자가 A안(매니저에 ZOrder 파라미터 추가)을 확정했고 plan·spec 에 반영이 끝났다** — `OpenUI(FName, int32 ZOrder = 0)` + `OpenSpyUI` 패스스루, 브라우저는 **200**. plan Task 8 Step 1 이 `AddToViewport()` 호출부 2곳(신규 생성·캐시 재사용)을 모두 명시한다. 아래 §3-1·§3-3 은 **결정 이력**으로 남긴다.

### 3-1. 발단이 된 문제 (개정 전 코드 기준)

브라우저가 뜨는 순간 화면에는 위젯이 **둘** 있다.

| 위젯 | 부착 방식 | ZOrder | 화면을 덮는 부분 |
|---|---|---|---|
| 로딩 UI (persistent) | `AddViewportWidgetContent(..., ZOrder)` | **100** | 전체 화면 불투명 배경 `Border` `#08090B` (`loading-scene.md` §5-2) |
| 방 목록 (일반 UI, **개정 전**) | `AddToViewport()` (인자 없음) | **0** | 브라우저 전체 |

브라우저가 로딩 UI 보다 **아래** 순서로 붙으면, 로딩 UI 의 전체 화면 불투명 배경이 브라우저를 통째로 가린다. 그러면 사용자에게는 "로딩이 끝났는데 아무 일도 일어나지 않는" 화면만 남는다 — 이 기획의 검증 가설이 첫 줄에서 무너진다. 로딩 위젯의 배경 `Border` 는 C++ 바인딩이 없어 숨길 수도 없다(§1-2).

> **엔진의 정확한 오버레이 정렬 규칙을 이 문서가 단정하지는 않는다.** 단정하는 것은 **요구**와 **검증**이다: 브라우저가 로딩 UI 위에 보여야 하고, 그것을 첫 실행에서 눈으로 확인한다(M-SB-1). 이 검증 항목은 개정 반영 여부를 확인하는 용도로 **그대로 유지**한다.

### 3-2. 확정 요구값

| 항목 | 값 |
|---|---|
| 방 목록 UI 의 렌더 순서 | **persistent 로딩 UI(ZOrder 100)보다 위** |
| 확정 ZOrder | **200** |

- **200 인 이유**: 로딩 UI(100)보다 확실히 위이면서, 이후 추가될 다른 persistent UI 가 100~199 구간을 쓸 여지를 남긴다. 101 같은 인접값은 나중에 UI 가 하나만 늘어도 다시 충돌한다.
- **브라우저는 자기 배경을 그린다**(§4-4 배경 `Border`, 전체 화면 `#08090B` 불투명). 위에 얹히므로 아래의 로딩 배경에 의존할 수 없고, 의존해서도 안 된다.
- spec §5-2 의 "브라우저 아래 깔려 있던 persistent 로딩 UI" 라는 문장은 **이 요구값이 충족될 때에만 참**이 된다. 이 절은 spec 을 바꾸는 것이 아니라 성립시키는 값이다.

### 3-3. 해소 경로 3안 — **A 로 확정됨** (이력)

| 경로 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **A** | `USKUIManager::OpenUI` / `USpyUIManager::OpenSpyUI` 에 ZOrder 인자 추가 | 일반 UI 전반에 재사용 가능한 정공법. spec §5-2 "일반 UI" 결정 유지 | 재사용 플러그인(`SKUICore`) 변경 | **채택 (사용자 확정 · plan·spec 반영 완료)** |
| B | 브라우저를 `OpenPersistentSpyUI(SessionBrowser, 200)` 로 연다 | 코드 추가 없이 ZOrder 지정 가능 | spec §5-2 의 "일반 UI(persistent 아님)" 결정을 뒤집는다. persistent 는 트래블 생존이 목적이라 의미도 어긋난다 | 기각 |
| C | 로딩 위젯의 배경 `Border` 를 `BindWidgetOptional` 로 노출해 브라우저 표시 중 숨긴다 | 게임 모듈 안에서 끝남 | 렌더 순서 자체는 그대로라 **클릭 히트 테스트가 로딩 위젯에 먹힐 위험이 남는다.** 근본 해소가 아님 | 기각 (임시 회피) |

**결과**: 요구값(§3-2)과 경로(A)가 모두 확정됐다. 이 기획서에 남는 값은 **브라우저 ZOrder = 200** 하나이고, 그 값이 실제로 적용됐는지는 M-SB-1 로 확인한다.

## §4 방 목록 화면 레이아웃

> 디자인 해상도 **1920×1080**, `loading-scene.md` §5-2 좌표계 준수. 아래 위치는 Canvas Panel 앵커/정렬 기준이며, 별도 표기가 없으면 앵커·정렬 모두 `(0.5, 0.5)`(화면 중심)다.

### 4-1. 패널 타입 — **`ScrollBox`**, 가시 **6행** (plan Task 9 Step 3 확정)

| 항목 | 값 |
|---|---|
| `SessionListBox` 위젯 타입 | **`ScrollBox`** |
| 가시 행 수 | **6행** (7번째 행 밴드 상단 40px 노출) |
| **행 슬롯 높이(pitch)** | **80px** — **행 위젯 자체가 80px 이다** (§4-3) |
| 행 밴드 높이 (배경·콘텐츠) | **72px**, 슬롯 상단 정렬 |
| 행 간격 | **8px** — 슬롯 패딩이 아니라 **행 하단에 내장된 여백** (§4-3) |
| 스크롤바 | 두께 **8px**, **항상 표시**(`AlwaysShowScrollbar = true`), **스크롤바 주변 패딩 = 0** |

**근거**

- **`MaxSearchResults = 20`(§2-2) 이므로 최대 20행이 도착한다.** 콘텐츠 높이 = `20 × 80 = 1600px` 로 가시 영역(520px)의 3배다. `VerticalBox` 로 두면 초과분이 패널 밖으로 흘러 **잘리고 접근 불가**가 된다 — 사용자는 목록에 더 있다는 사실조차 알 수 없다. `ScrollBox` 는 이 경우에도 전부 접근된다.
- **plan 의 C++ 은 이 결정에 독립적으로 유지된다.** `SessionListBox` 가 `UPanelWidget` 으로 선언돼 `AddChild`/`ClearChildren` 만 쓰므로(plan Task 7 각주), `ScrollBox` 로 BindWidget 이 그대로 충족된다 — **C++ delta 0**. 이 성질을 지키기 위해 **행 간격(8px)을 슬롯 패딩이 아니라 행 위젯 안에 내장한다**(§4-3) — 런타임 `AddChild` 가 만드는 슬롯을 C++ 이 건드릴 필요가 없다.
- **6행 가시**: 행 위젯 자체가 80px(밴드 72 + 하단 여백 8)이므로 6행이 차지하는 높이는 `6 × 80 = 480px` 이고, 그중 **보이는 밴드**는 `6 × 72 + 5 × 8 = 472px` 다. 패널 높이를 **520px** 로 두면 7번째 행(콘텐츠 오프셋 `6 × 80 = 480`)의 밴드 상단 **40px**(`520 − 480`)이 잘린 채 보인다. **잘린 행이 보이는 것 자체가 "아래에 더 있다"는 유일한 신호**이므로 의도적으로 딱 떨어지지 않게 잡았다.
- **스크롤바 항상 표시 + 주변 패딩 0**: 자동 숨김이면 방 수가 6 이하일 때 스크롤바가 사라지며 콘텐츠 가용 폭이 `1032 → 1040` 으로 **8px 넓어져 컬럼 위치가 흔들린다.** 또한 스크롤바 주변 패딩을 **명시적으로 0** 으로 두어야 가용 폭 검산 `1040 − 8 − 0 = 1032`(§4-3)가 성립한다 — **엔진 기본값을 가정하지 않고 값으로 못박는다.**

**대안 비교**

| 안 | 패널 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | `VerticalBox` 고정 목록 | 가장 단순, 스크롤 입력 불필요 | 7행 이상이면 잘려서 접근 불가. `MaxSearchResults = 20` 과 정면 충돌 | 기각 |
| **B** | **`ScrollBox` 6행 가시** | 20행까지 전부 접근. C++ delta 0. 잘린 7행이 스크롤 힌트 | 스크롤 입력이 필요(마우스 휠·드래그) | **채택** |
| C | `ScrollBox` + 페이지 버튼 | 휠 없이도 이동 | 버튼 2개 추가 = BindWidget·코드 delta. 6행 화면에 과한 장치 | 기각 |

#### 4-2-5. 배치 근거

**가로 (2단 구성 — 이번 변경)**

- **로고는 왼쪽, 목록은 오른쪽** — 좌→우 읽기 순서에서 왼쪽은 "여기가 어디인가"(정체, 한 번 읽고 다시 보지 않는 정적 정보)이고 오른쪽은 "무엇을 할 것인가"(스크롤·클릭이 반복되는 상호작용 영역)다. **반복 조작이 일어나는 쪽을 오른쪽에 두면 포인터가 화면 중앙~우측에 머물러 이동 거리가 짧다.** 반대로 두면 정적인 로고 위를 포인터가 계속 지나간다.
- **목록 폭을 1152 → 1040 으로 줄인 대가와 이득** — 컬럼 하나를 로고에 내주면서 행 폭이 `1144 → 1032`(−112)로 줄고, 그 감소분은 전부 가변 폭인 방 이름(`660 → 548`)이 흡수한다(§4-3-3). 인원·핑·참가 버튼은 고정 폭이라 **표시가 달라지지 않는다.** 대신 화면 왼쪽 절반이 비지 않아 "목록만 떠 있는 임시 화면" 이 아니라 **완성된 한 화면**으로 읽힌다.
- **버튼·상태 문구를 화면 중앙(960)이 아니라 목록 컬럼 중심(1280)에 맞춘다** — 두 버튼은 **목록에 딸린 액션**이다(새로고침 = 이 목록을 갱신, 방 만들기 = 이 목록에 들어갈 방이 없을 때의 대안). **액션은 그 대상에 정렬한다.** 화면 중앙에 두면 버튼 블록이 로고 컬럼 위로 걸쳐 어느 쪽에 속한 조작인지 흐려지고, 목록 좌측 경계(760)와도 어긋나 두 컬럼 사이에 떠 있는 덩어리가 된다. `StatusText` 도 같은 이유로 1280 에 맞춘다.

**세로 (이전 판에서 유지)**

- **목록을 화면 중심보다 60px 위로** — 목록이 주 정보이고 그 아래에 액션(버튼)과 상태(문구)가 순서대로 쌓이는 **위→아래 읽기 흐름**을 만든다. 정확히 중앙에 두면 아래쪽 요소들이 하단으로 밀려 로딩바 영역과 가까워진다.
- **버튼을 목록 아래 가로로 나란히** — 목록의 "방 고르기"와 버튼의 "새로 찾기 / 직접 만들기"는 **동등한 층위의 선택지**다. 세로로 쌓으면 아래쪽 버튼이 부차적으로 읽힌다.
- **`HostButton`(방 만들기)을 오른쪽(1400)에** — 이 화면에서 "방 만들기"는 결과가 확정적인(반드시 인게임으로 진입하는) 주 액션이고, "새로고침"은 화면에 머무는 보조 액션이다. 주 액션을 오른쪽에 두는 것이 확인/진행 버튼의 일반 배치와 맞는다.
- **`StatusText` 를 버튼 아래에** — 상태 문구는 목록(있음/없음)과 액션(성공/실패) **양쪽의 결과**를 통지하므로 둘 다의 하류에 둔다. 목록 영역 안에 두면 결과가 있는 상태(목록 + 에러)에서 행과 겹친다.
- **로고를 목록과 같은 세로 중심(480)에** — 두 컬럼이 같은 축에 걸려야 2단이 나란한 한 쌍으로 읽힌다. 로고를 위로 붙이면 오른쪽 컬럼만 아래로 처진 비대칭이 된다.

### 4-3. 행(`WBP_SessionRow`) 위젯 구조 — **여백 내장형 80px 행**

#### 4-3-1. 왜 여백을 행 안에 넣는가 (결정)

행은 런타임에 `SessionListBox->AddChild(Row)` 로 붙는다(plan Task 7). **그 슬롯은 WBP 디자이너에 존재하지 않으므로, 슬롯 패딩으로 행 간격을 만들 수단이 이 설계에는 없다.** 두 갈래를 놓고 골랐다.

| 안 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| a | C++ 이 `AddChild` 반환값을 `UScrollBoxSlot` 으로 캐스팅해 `SetPadding(0,0,0,8)` | 행 위젯이 단순해짐 | §4-1 의 **"C++ delta 0" 주장이 거짓이 된다.** plan Task 7 이 패널을 `UPanelWidget` 으로 추상화한 근거(승인 전 레이아웃에 C++ 을 묶지 않는다)를 되돌린다 — 얻는 결과는 b 와 동일 | 기각 |
| **b** | **행 위젯 자체를 80px 로 만들고 상단 72px 밴드 + 하단 8px 여백** | WBP 안에서 끝나 **C++ delta 0 과 `UPanelWidget` 추상화가 모두 유지**된다. 슬롯 정렬·패딩의 엔진 기본값에 의존하지 않는다 | 행 위젯 트리에 층이 하나 늘어난다(`SizeBox` + `VerticalBox`) | **채택** |

**그 결과 §4-1 의 pitch 80 은 "슬롯 간격"이 아니라 "행 위젯의 높이"로 성립한다.** 행이 스스로 폭·높이를 선언하므로 슬롯 설정이 무엇이든 검산이 흔들리지 않는다.

#### 4-3-2. 위젯 트리 (확정)

```
SizeBox_Row            WidthOverride = 1032, HeightOverride = 80        ← 행 루트
└ VerticalBox
   ├ [슬롯1 Size=Auto] SizeBox_Band   HeightOverride = 72
   │   └ Border  (행 배경 #1A1F24, Padding 0)
   │       └ HorizontalBox  (아래 4-3-3 의 7슬롯)
   └ [슬롯2 Size=Auto] Spacer         Size = (0, 8)                     ← 다음 행과의 간격
```

- **행 폭을 행이 직접 선언한다**(`WidthOverride = 1032`) — `ScrollBox` 자식 슬롯의 수평 정렬 기본값을 가정하지 않기 위해서다. `1032 = 1040 − 스크롤바 8 − 스크롤바 주변 패딩 0`(§4-1·§4-2-1)이므로 가로 넘침도 없다.
- **세로 구조(80 = 밴드 72 + `Spacer` 8)는 2단 구성 변경의 영향을 받지 않는다** — 바뀐 것은 `WidthOverride` 숫자 하나뿐이다.
- `SizeBox_Row` · `SizeBox_Band` · `Spacer` 는 BindWidget 대상이 아니다 — 이름은 구현 편의값이고, **필수 이름은 `RoomNameText` · `PlayersText` · `PingText` · `JoinButton` 뿐**이다(plan Task 6).

#### 4-3-3. 컬럼 — `HorizontalBox` 7슬롯

밴드 폭 **1032px**. 좌→우 순서는 task 지정(방 이름 / 인원 / 핑 / 참가)을 따른다. **모든 슬롯 `Size = Auto`, 폭은 `SizeBox` 로 고정한다.**

| 1 | `Spacer` (좌측 패딩) | **24** | — | — |

**검산**: `24 + 548 + 140 + 120 + 16 + 160 + 24 = 1032` ✅ (밴드 폭과 정확히 일치)

> **2단 구성 변경으로 바뀐 값은 방 이름 폭 하나다** — 행 폭이 `1144 → 1032`(−112)로 줄면서 가변 폭인 `RoomNameText` 가 `660 → 548`(−112)로 전부 흡수했다. 인원·핑·참가 버튼·좌우 패딩·버튼 앞 간격은 **고정 폭이라 값도 표시도 그대로**다.

- **`Size = Fill` 을 쓰지 않는 이유**: Fill 비율은 남는 폭을 재분배하므로 밴드 폭이 조금만 달라져도 컬럼이 전부 움직여 위 검산이 무의미해진다. 폭을 `SizeBox` 로 못박으면 컬럼 위치가 결정값이 된다.
- **말줄임(`…`) 을 성립시키는 지정** — 고정 폭만으로는 말줄임이 나지 않는다. `RoomNameText` 에 **`Auto Wrap Text = false`**, **`Overflow Policy = Ellipsis`**, 감싸는 `SizeBox` 에 **`Clipping = Clip to Bounds`** 를 함께 지정한다. 셋 중 하나라도 빠지면 긴 이름이 줄바꿈되거나(행 높이 붕괴) 옆 컬럼을 밀어낸다.
- **수직 정렬**: 슬롯 2~4 의 텍스트는 `VerticalAlignment = Center`. 슬롯 6 의 `JoinButton` 은 높이 44, 밴드 높이 72 → **상하 여백 각 14px**, `VerticalAlignment = Center`. 검산 `14 + 44 + 14 = 72` ✅
- **폭 배분 근거**: 인원(`2 / 4`)·핑(`30 ms`)은 글자 수가 고정에 가까운 계측값이라 좁은 고정 폭이면 충분하고, **가변 길이인 방 이름에 남는 폭을 전부 준다**(548 = 행 폭 1032 의 **53%**). `"{0}의 방"` 포맷(§2-3)에서 **548px 는 Roboto 20 기준 한글 약 25자** — 방 이름은 "닉네임 + `의 방`(3자)" 이므로 닉네임이 22자를 넘을 때에만 말줄임이 걸린다. **실사용에서는 드물다.** (2단 구성 이전 값 660px = 약 30자 기준 서술을 이 값으로 정정했다.)
- **정렬 근거**: 방 이름은 좌측 정렬(읽기 시작점 정렬), 인원은 가운데(`/` 를 축으로 좌우 대칭), 핑은 우측(자릿수가 달라도 단위 `ms` 가 세로로 정렬돼 계측값으로 읽힌다).
- **행 정렬 순서(어떤 방을 위에 둘지)**: **검색 결과 순서 그대로.** 핑·인원 정렬을 넣지 않는다 — 정렬은 코드 추가이고(plan Task 7 `HandleSessionsFound` 는 받은 순서로 `AddChild` 한다), LAN 환경에서는 결과가 소수라 정렬 이득이 없다. 명시적 결정이며 누락이 아니다.

### 4-6. 위젯 트리 배치 순서 (z-order) — 반드시 지킬 것

UMG 는 캔버스 자식 목록의 **나중 항목을 위에** 그린다. 배경을 마지막에 추가하면 화면이 배경색으로만 나온다(`loading-scene.md` §5-2 가 같은 이유로 순서를 못박았다).

**`WBP_SessionBrowser` 배치 순서**: ① 배경 `Border` → ② **로고 `Image`**(브러시 `T_Logo`, §4-2-4) → ③ `SessionListBox` → ④ `RefreshButton` → ⑤ `HostButton` → ⑥ `StatusText`

- 로고는 **배경 바로 다음**이다. 다른 요소와 겹치지 않으므로(로고 `120~680` / 목록 컬럼 `760~1800`) 순서가 표시에 영향을 주지는 않지만, **배경보다 앞(= 위)** 이어야 한다는 것만은 배경 규칙상 반드시 지킨다.

**`WBP_SessionRow`**: 컬럼은 `HorizontalBox` 슬롯 순서(§4-3-3 의 1→7)가 곧 좌→우 배치이고, 행 배경 `Border` 는 그 `HorizontalBox` 의 **부모**다(§4-3-2 트리) — 캔버스 z-order 규칙이 아니라 컨테이너 중첩으로 성립하므로 배경이 컬럼을 덮지 않는다.

## §5 문구

> 모든 문구는 `networked-loading-transition.md` §4-1 규약과 대조했다: **느낌표·"오류!" 등 격앙 표현 0건**, **전부 완결 문장형 상태 통지**, **실패 원문(OSS/엔진 영문) 화면 노출 0건**(plan Task 7 `HandleSessionError` 가 `Detail` 을 로그로만 남긴다 — 유지).

### 5-1. `MakeStatusMessage` 및 안내 문구 — **8종 전부 유지 확정**

| # | 상황 (`Op` / `Error`) | 확정 문구 | plan 값 | 판정 |
|---|---|---|---|---|
| 1 | 검색 결과 0건 (에러 아님) | **방이 없습니다** | 동일 | **유지 확정** |
| 2 | `NoOnlineSubsystem` (모든 Op) | **온라인 기능을 사용할 수 없습니다** | 동일 | **유지 확정** |
| 3 | `Hosting` 실패 | **방을 만들지 못했습니다** | 동일 | **유지 확정** |
| 4 | `Finding` 실패 | **방 목록을 불러오지 못했습니다** | 동일 | **유지 확정** |
| 5 | `Joining` 실패 | **방에 들어가지 못했습니다** | 동일 | **유지 확정** |
| 6 | 그 외 Op 실패 (`default`) | **온라인 요청을 처리하지 못했습니다** | 동일 | **유지 확정** |
| 7 | `Busy` (중복 입력 가드) | **표시 없음** (빈 문자열) | 동일 | **유지 확정** |
| 8 | `None` | **표시 없음** (빈 문자열) | 동일 | **유지 확정** |

**유지 근거**

- **1~6 은 전부 "무엇을 못 했다" 를 주어-서술어로 끝맺는 완결 문장**이라 §4-1 의 "라벨이 아니라 상태 통지" 요건을 이미 충족한다. `networked-loading-transition.md` 가 `"서버 접속 실패"` → `"서버에 연결하지 못했습니다"` 로 고쳤던 것과 **같은 형태로 이미 쓰여 있다** — 고칠 이유가 없다.
- **Op 별로 문구가 갈리는 것이 옳다.** 사용자가 방금 누른 버튼과 실패 문구가 대응해야 원인을 짐작할 수 있다("방 만들기를 눌렀는데 목록을 못 불러왔다" 같은 어긋남이 없다).
- **2 를 Op 보다 우선하는 것도 옳다.** 온라인 서브시스템 자체가 없으면 어떤 Op 를 눌러도 결과가 같으므로, Op 별 문구보다 **원인을 직접 말하는 문구**가 더 유용하다.
- **7·8 무음 유지** — 중복 입력 가드는 사용자 잘못이 아니다. 연타할 때마다 문구가 튀면 그것이 오히려 에러처럼 읽힌다(plan Task 10 Step 3 이 이 무음을 검증 항목으로 둔다).
- **6(`default`)은 task 목록에 없었지만 plan 코드에 존재**한다. 누락으로 오해되지 않도록 유지 확정으로 명시한다.

### 5-2. 진행 상태 문구 — **3종 신규 확정** (plan 대비 delta)

**문제**: 현재 plan 은 검색·생성·조인을 시작할 때 `SetStatus(FString())` 으로 **상태 줄을 비운다**. 그런데 OSS Null 의 LAN 검색은 브로드캐스트 응답을 수 초간 수집한 뒤에야 완료되므로, 그 사이 화면은 **행도 없고 문구도 없는 완전한 무반응 상태**가 된다. 특히 브라우저가 처음 뜰 때(`NativeConstruct` 자동 검색)는 **빈 화면 → 수 초 정지 → "방이 없습니다"** 순서로 보여 "고장" 으로 읽힌다. 게다가 이 구간의 재클릭은 `Busy` 무음 처리(§5-1 #7)라 **연타해도 아무 반응이 없다.**

**확정 — 시작 시점에 진행 문구를 표시한다.**

| 시점 (plan 위치) | 확정 문구 | plan 값 |
|---|---|---|
| 검색 개시 — `NativeConstruct` 자동 검색 / `OnRefreshClicked` | **방 목록을 불러오는 중입니다** | `SetStatus(FString())` (빈 문자열) |
| 방 생성 개시 — `OnHostClicked` | **방을 만드는 중입니다** | `SetStatus(FString())` |
| 조인 개시 — `HandleRowClicked` | **방에 들어가는 중입니다** | `SetStatus(FString())` |
| **세션 정리 진행 중** (`Destroying`) — 아래 §5-2-1 이 요구 | **이전 방을 정리하는 중입니다** | (해당 문구 없음) |

- **문구 톤은 §5-1 과 동일**하다(완결 문장형, 느낌표 없음, 원문 비노출).
- **시그니처·구조 변경 없음** — 기존 `SetStatus(const FString&)` 호출부 4곳의 **인자 문자열만** 바뀐다. 어떤 문구를 넣을지는 §5-2-1 의 결정 규칙이 정한다.

#### 5-2-1. 진행 문구는 **"지금 진행 중인 op"** 를 말한다 — 요청한 op 가 아니라

**요청을 보내면서 그 op 의 문구를 먼저 쓰면 화면이 거짓말을 한다.** plan Task 3 `CanStartOp` 은 `CurrentOp == None` 일 때만 허용하므로 **종류가 다른 op 가 진행 중이어도 `Busy` 로 거부**된다. 두 증상이 실재한다.

1. **교차 op** — 호스팅 진행 중에 새로고침을 누르면 `OnRefreshClicked` 가 "방 목록을 불러오는 중입니다" 로 덮어쓰지만 `FindSessions` 는 거부된다 → **실제로 진행 중인 것(호스팅)과 다른 문구가 남는다.**
2. **재진입** — plan Task 8 Step 7 의 접속 실패 복구는 `DestroyCurrentSession()` **직후** 브라우저를 여는데, `NativeConstruct` 의 자동 `FindSessions()` 가 파괴 op 와 겹쳐 거부될 수 있다 → 검색이 돌지 않은 채 검색 문구만 남는다. 이 경로는 plan Task 10 Step 4 가 정면으로 검증한다.

**확정 규칙 — 한 문장**: `SetStatus` 에 넣을 진행 문구는 **요청 직전 `GetCurrentOp()`(plan Task 4 에 이미 존재)가 가리키는 op 의 문구**로 하고, 그것이 `None` 이면 **이번에 요청하는 op 의 문구**로 한다.

| 요청 직전 `GetCurrentOp()` | 표시할 진행 문구 | 그때 실제로 일어나는 일 |
|---|---|---|
| `None` | 이번에 요청하는 op 의 문구 (`Finding` → 방 목록을 불러오는 중입니다 / `Hosting` → 방을 만드는 중입니다 / `Joining` → 방에 들어가는 중입니다) | 요청이 수락된다 |
| `Finding` | **방 목록을 불러오는 중입니다** | 새 요청은 `Busy` 로 무시됨 |
| `Hosting` | **방을 만드는 중입니다** | 〃 |
| `Joining` | **방에 들어가는 중입니다** | 〃 |
| `Destroying` | **이전 방을 정리하는 중입니다** | 〃 |

- **명령 호출 자체는 그대로 보낸다** — 서브시스템의 가드가 단일 진실이고, 위젯이 op 수락 여부를 예측해 호출을 건너뛰면 판정 로직이 두 곳으로 갈린다. 위젯은 **문구만** 결정한다.
- 이 규칙 하나로 증상 1·2 가 모두 "화면이 사실을 말한다" 로 정리된다.
- **표시 규칙은 완전히 확정됐고, 코드 형태(헬퍼 함수로 뺄지 호출부 4곳에 둘지)는 gameplay-programmer 판단**이다.

**함께 확정 — 무음 사유(`Busy`/`None`)는 진행 문구를 지우지 않는다**

위 규칙만으로는 부족하다. 거부된 요청이 `OnSessionError(Op, Busy)` 를 브로드캐스트하고, `HandleSessionError` 가 `SetStatus(MakeStatusMessage(...))` = `SetStatus("")` 를 호출하면 **`StatusText` 가 `Collapsed` 로 접혀** 방금 세운 문구가 사라진다.

| 항목 | 확정 |
|---|---|
| `MakeStatusMessage` 가 빈 문자열을 반환한 경우(`Busy` · `None`) | **`SetStatus` 를 호출하지 않고 그대로 둔다** — 진행 문구가 유지된다 |
| 그 외 사유 | 기존대로 `SetStatus(에러 문구)` 로 덮는다 |
| 로그 | `Detail` 원문 로그는 사유와 무관하게 그대로 남긴다 (변경 없음) |

- **무음 의도는 그대로 지켜진다** — 중복 입력에 **새 문구를 띄우지 않는다**는 것이 원래 의도이고(§5-1 #7), 진행 중이라는 통지가 남는 것은 그 의도와 어긋나지 않는다.

- plan Task 10 Step 3 의 기대 동작이 바뀐다: "연타 시 에러 문구가 튀지 않는가" → **"연타해도 진행 문구가 유지되고 에러 문구가 튀지 않는가"**.

**문구가 굳을 수 있는 경로 — 하나 남으며, 회복 수단이 있다 (사실 기록)**

이전 판의 "문구가 남아 굳는 경로가 없다" 는 서술은 **틀렸다.** 정정한다: 문구를 덮는 경로는 검색 성공(`HandleSessionsFound`) · 실패(에러 문구) · 호스팅·조인 성공(`CloseForTravel()`) 셋인데, **위 증상 2(파괴 op 와 겹쳐 자동 검색이 거부된 경우)에는 셋 중 어느 것도 발생하지 않는다.** 그 상태에서는 목록이 빈 채로 "이전 방을 정리하는 중입니다" 가 남는다.

- 이 경우 **문구는 사실을 말하고 있다**(정리가 실제로 진행 중이었다). 잘못된 통지가 아니라 **갱신되지 않는 통지**다.
- **회복 수단은 항상 활성인 `새로고침` 버튼**이다. 파괴는 즉시 끝나므로 그다음 새로고침은 정상 수락된다.

- **`StatusText` · `PingText` 는 `BindWidgetOptional`**(plan Task 6·7)이라 WBP 에서 빠져도 컴파일이 통과한다. **본 기획서 기준 두 위젯은 필수 배치다** — `StatusText` 가 없으면 화면에 표시되는 문구 10종(안내 1 + 실패 5 + 진행 4, §5)이 전부 조용히 사라진다.
- **색·서체**: §4-4 표 그대로 (배경 `#08090B` / 행 배경 `#1A1F24` / 방이름 `#E6F4F6`@0.85 20 / 인원 `#E6F4F6`@0.85 18 / 핑 `#E6F4F6`@0.55 18 / 상태 `#E0A44E` 22, 전부 Roboto Regular)
- **버튼 스타일**: Normal `#1A1F24` / Hovered `#5AC8D8` / Pressed `#48A0AD`, `JoinButton` Disabled `#13161A` + 라벨 `#E6F4F6`@0.25 — §4-4
- **라벨**: `HostButton` "**방 만들기**" / `RefreshButton` "**새로고침**" / `JoinButton` "**참가**" — §5-3
- **배치 순서(z-order)**: 브라우저 캔버스 ① `Border` → ② **로고** → ③ `SessionListBox` → ④ `RefreshButton` → ⑤ `HostButton` → ⑥ `StatusText`. 행은 캔버스가 아니라 컨테이너 중첩(§4-3-2)이라 z-order 규칙이 적용되지 않는다 — §4-6
- **추가 자식 위젯**: 배경 `Border`(브라우저 1개 + 행 1개)와 **로고 1개**(§4-2-4) 외에 **타이틀·컬럼 헤더·장식 텍스트를 넣지 않는다.** 근거: 컬럼 내용(`2 / 4`, `30 ms`, 버튼 라벨)이 스스로 의미를 말하므로 헤더가 정보를 더하지 않고, `loading-scene.md` §5-3 의 "정보 없는 정적 라벨 미추가" 결정과 같은 톤이다. **로고는 장식이 아니라 2단 구성의 좌측 컬럼 자체**라 이 규칙의 예외가 아니다.

### 8-6. 렌더 순서 (**결정 완료**)

- 방 목록 UI 의 **ZOrder = 200** — persistent 로딩 UI(100)보다 위 (§3-2).
- 해소 경로는 **A안(매니저에 ZOrder 파라미터 추가)으로 사용자 확정**됐고 plan·spec 에 반영 완료다(§3). 이 기획서가 남기는 값은 **200** 하나이며, 적용 여부는 M-SB-1 로 확인한다.

### 8-7. 문구 (뷰 로직 값)

- `MakeStatusMessage` 반환 문자열 **5종**(`NoOnlineSubsystem` · `Hosting` · `Finding` · `Joining` · `default`) + 무음 2종: **§5-1 표 그대로 유지** (`MakeStatusMessage` 함수 자체는 코드 변경 없음).
- 빈 목록 안내 `"방이 없습니다"`: **유지** (plan Task 7 `HandleSessionsFound`).
- 진행 상태 문구 **4종**: **§5-2 표의 문자열**을 쓰되, **어떤 문구를 넣을지는 §5-2-1 의 `GetCurrentOp()` 기반 결정표**가 정한다 (`NativeConstruct` / `OnRefreshClicked` / `OnHostClicked` / `HandleRowClicked` 4개 호출부, `SetStatus` 시그니처 불변). `GetCurrentOp()` 는 plan Task 4 에 이미 있으므로 **SKOnline 변경 없음**.
- `HandleSessionError`: **`MakeStatusMessage` 결과가 빈 문자열이면 `SetStatus` 를 호출하지 않는다**(진행 문구 유지). 그 외에는 기존대로 덮는다. `Detail` 로그는 사유와 무관하게 유지 — §5-2-1.
- 실패 원문(`Detail`)은 **화면에 표시하지 않는다** — 로그 전용. plan 이 이미 그러함, 유지.

### 8-8. 검증 절차 추가 (plan Task 10)

- **Task 10 Step 1 의 첫 항목으로 M-SB-1 을 넣는다**: "로딩 완료 직후 **방 목록이 화면에 보이는가**, 그리고 `RefreshButton` 클릭이 브라우저로 전달되는가". 이것이 실패하면 이후 모든 항목이 검증 불가다.
- Task 10 Step 2 에 **M-SB-2**(두 호스트의 방 이름이 구분되는가)와 **M-SB-4**(2인 스폰 겹침 관찰)를 함께 관측 항목으로 붙인다.
- **Task 10 Step 2 3항(성공 기준 "둘이 서로 보이고 움직임이 동기화되는가")에 오독 방지 주석을 넣는다**: **"`DevMap` 의 PlayerStart 가 1개(§1-2)이므로 합류 직후 두 캐릭터가 같은 지점에 스폰돼 서로 밀려나는 것은 예상 동작이며 동기화 실패가 아니다. 동기화 판정은 밀림이 끝난 뒤 서로의 이동이 상대 화면에 따라오는지로 한다."** (맵 변경은 요구하지 않는다 — §2-1-5)
- Task 10 Step 3 의 2항 기대 동작을 **"버튼을 연타해도 진행 문구가 유지되고 에러 문구가 튀지 않는가"** 로 바꾼다(§5-2-1). 같은 Step 에 **M-SB-3**(진행 문구가 뜨는가 / 실패로 오독되는가)을 붙인다.
