# 로딩 씬 — 페이싱 · 표기 · 레이아웃 기획

> **이 문서의 범위**: 이미 확정된 로딩 씬 구조 안에 들어갈 **도메인 값** — `MinDisplaySeconds` · `AssetPhaseWeight` · 로딩바 체감(보간 여부) · 퍼센트 표기 규칙 · 화면 레이아웃 · 전환 순간 UX · PIE 검수 한계 — 의 확정과 그 근거.
> 클래스 구조 · 진행률 합성 공식 · 델리게이트 · 위젯 바인딩 이름 · 파이프라인 순서는 [spec](../superpowers/specs/2026-07-22-loading-scene-design.md) 과 [plan](../superpowers/plans/2026-07-22-loading-scene.md) 에서 이미 확정됐다. **이 문서는 그것을 다시 제안하지 않고 뒤집지도 않는다.**

---

- **목표** — 로딩 화면이 "부팅 대기"가 아니라 "게임이 준비되는 과정"으로 읽히도록, 표시 시간·가중치·표기·레이아웃 값을 근거와 함께 확정한다.
- **검증 가설** — 부팅 시 플레이어의 시선이 로딩바에 안착한 **뒤에도** 바의 대부분 구간이 남아 있고, 바가 눈에 띄게 멈추거나 튀지 않은 채 100% 에 도달해 게임플레이 맵으로 넘어가는가.
- **현재 단계 범위 적합성** — `project.md` 의 `stage` / `stage_goal` 은 **(사용자 확정 대기)** 이고 컨셉서 §1 세부 톤 · §2 · §4 · §5 도 미확정이다. 따라서 단계 부합 여부를 단정하지 않는다. 대신 **사용자 승인이 완료된 spec(2026-07-22-loading-scene-design.md)의 목적·범위를 이 기획서의 범위 경계로 삼는다.** spec §9 범위 밖(메인 메뉴, 팁·배경 로테이션, 취소·재시도, 부팅 동기 로드 리팩터링)은 §8 에 명시 제외로 남기고 본문에서 다루지 않는다.
- **핵심 메커니즘** — 표시 진행률은 `Displayed = min(Raw, Elapsed / MinDisplaySeconds)` 로 **시간 램프에 눌린 채** 오른다. 이 문서는 그 램프의 길이(`MinDisplaySeconds = 2.5`)와 두 로드 단계의 배분(`AssetPhaseWeight = 0.9` — **실측 확정**)을 **실제 소요 시간 비율에 맞춰** 정해, 시간 램프가 대부분 구간에서 상한이 되도록(= 바가 프레임 단위로 매끄럽게 차도록) 만든다.

## §2 `MinDisplaySeconds` — 최종값 **2.5초**

### 2-1. 결정

| 항목 | 값 |
|---|---|
| `USpyLoadingConfig::MinDisplaySeconds` | **2.5** |
| 플랜 기본값 | 2.0 (→ 이 기획서가 2.5 로 확정) |

### 2-2. 근거 — 인지 예산 분해 (**판단에 따른 선택값**)

> **이 값은 계산으로 유도한 것이 아니라 판단에 따른 선택이다** — §5-2 의 바 두께 6px 과 같은 성격이다. 아래 분해는 그 판단이 어떤 크기의 것들을 저울에 올렸는지 보이기 위한 것이고, 세 항목 중 문헌 근거가 있는 것은 (b) 하나뿐이다. (a)·(c) 는 **추정**이며 §1-3 에 해소 경로(M1·M3)와 함께 등재돼 있다.

로딩 화면의 최소 표시 시간은 "지루하지 않을 만큼"이 아니라 **플레이어가 화면을 인지하고, 바가 움직인다는 사실을 판정하고, 그 움직임을 실제로 지켜보는 데 필요한 시간의 합**으로 잡는다.

| 구간 | 소요 | 근거의 성격 |
|---|---|---|
| (a) 로딩 맵 첫 프레임 + 위젯 구성 안정화 | **0.2s** | **추정** (§1-3 등재, M1 로 해소) — 레벨 오픈 직후 몇 프레임은 히칭·해상도 확정 전이라 화면이 정보를 전달하지 못한다 |
| (b) 시선 도달 — 새 화면 요소로의 saccade + fixation | **0.25s** | **문헌 근거** — 단속성 안구운동 1회(30~80ms) + 목표 안착 후 고정(150~200ms). 화면이 바뀐 직후이므로 탐색 saccade 가 1~2회 든다 |
| (c) "움직이고 있다" 판정 | **0.3s** | **추정** (§1-3 등재, M3 로 해소) — 진행바처럼 느린 등속 변위는 단일 프레임으로 판정되지 않는다 |
| **인지 오버헤드 소계 (a+b+c)** | **0.75s** | 세 값 중 둘이 추정이므로 **소계도 추정치**다 |
| (d) 진행을 실제로 지켜보는 구간 | **잔여** | 이 구간이 짧으면 "로딩 화면을 봤다"가 아니라 "무언가 스쳤다"가 된다 |

위 소계(0.75s)를 전제로 후보값을 비교하면:

- **2.0s** — (d) = 1.25s. 시선이 안착하는 시점(0.45s)에 바는 이미 **22.5%**, "움직인다"를 판정하는 시점(0.75s)엔 **37.5%**.
- **2.5s** — (d) = 1.75s (전체의 **70%**). 시선 안착 시점 **18%**, 판정 완료 시점 **30%**.
- **상한 쪽** — 부팅 로딩은 "기대된 대기"라 주의 유지 한계(수 초 단위)에 한참 못 미치지만, **맵 1개짜리 빌드에서 3.0s 이상은 순수 대기로 인식**된다고 판단한다. 실제 로드가 1초 안에 끝나는 웜 부팅에서 3.0s 는 2초 가까이가 인위적 지연이 된다.

**선택** — 오버헤드 비율은 `0.75/2.0 = 37.5%`, `0.75/2.5 = 30%`, `0.75/3.0 = 25%` 로 **연속적으로 좋아진다. 여기에 "몇 % 아래여야 한다"는 임계값은 존재하지 않는다** — 그런 기준을 세우면 그건 유도가 아니라 결론의 재진술이다. 실제 판단은 다음 교환에서 내렸다: **2.0 은 "판정 완료 시점에 바가 이미 37.5%" 라는 손실을, 3.0 은 "웜 부팅에서 2초가 인위 지연" 이라는 손실을 낸다. 2.5 는 양쪽 손실을 각각 30% / 최대 1.5s 로 나눠 갖는 중간값이며, 그중 더 회복하기 어려운 손실(시작을 못 본 인상)을 줄이는 쪽에 가깝다.** 이 선택의 정당성은 계산이 아니라 §2-4 의 사용자 체감 판정으로 확정된다.

### 2-2-1. 실측이 흔든 전제 — **위젯이 1.23초 늦게 붙었다** (값은 유지, 해소는 구현 쪽)

§7 **M1** 실측에서, `# [SpyLoadingSubsystem] 로딩 시작` 시점과 로딩 위젯이 실제로 화면에 붙은 시점 사이에 **1.23초의 공백**이 관찰됐다. 원인은 `WBP_Loading` 클래스 자체가 이름 룩업으로 **비동기 로드**되기 때문이고, 그 결과 **`MinDisplaySeconds = 2.5` 중 첫 1.2초(49%)가 빈 화면**이었다.

이 사실은 §2-2 의 인지 예산 전제를 직접 흔든다. (a) "첫 프레임 안정화 0.2s" 로 잡았던 구간이 실제로는 **1.23s** 이며, 그만큼 (d) 관찰 구간이 잘려 나간다 — 2.5초 중 실효 관찰 시간은 계산상 `2.5 − 1.23 − 0.25(b) − 0.3(c) = 0.72s` 로, §2-2 가 목표한 1.75s 의 41% 에 불과하다.

**그럼에도 `MinDisplaySeconds` 값은 2.5 로 유지한다.** 이 공백은 시간을 늘려 덮을 문제가 아니라 **위젯이 늦게 뜨는 문제**이고, 시간으로 덮으면(예: 3.7s) 위젯 로드가 빨라진 뒤 곧바로 과도한 지연으로 남는다. **해소는 구현 쪽 — 로딩 위젯 클래스의 선(先)로딩** 에 맡긴다. 선로딩이 반영되면 (a) 는 §2-2 의 0.2s 가정에 근접하고 2.5 의 근거가 그대로 성립한다. 선로딩 반영 전까지는 §2-4 의 체감 판정 ①("바가 절반 이상 차기 전에 시선이 도달했는가")이 **위젯 지연 때문에** 아니오로 나올 수 있으므로, **①이 아니오여도 이 공백이 남아 있는 동안에는 `MinDisplaySeconds` 를 3.0 으로 올리지 않는다.**

### 2-3. 대안 비교

| 안 | 값 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | 1.5s | 부팅이 가장 빠름 | 인지 오버헤드가 절반(50%). 시선 안착 시 이미 30%, 바가 "깜빡" 지나간다 | 기각 |
| B | 2.0s (플랜 기본) | 무난. 관찰 구간 1.25s | 시선 안착 시점에 바가 이미 22.5% — 시작을 못 본다 | 기각 |
| **C** | **2.5s** | 관찰 구간 1.75s(70%). 인지 오버헤드 30% | 웜 부팅에서 최대 ~1.5s 인위 지연 | **채택** |
| D | 3.0s | 가장 여유로움 | 맵 1개 빌드에서 대기로 인식. 반복 부팅(개발 중) 비용이 큼 | 기각 |

### 2-4. 재조정 메트릭

§7 **M1** 에서 Standalone 실측 총 로드 시간 `T_total = T1 + T2` 를 얻는다.

- `T_total > 2.5s` 가 3회 연속이면 `MinDisplaySeconds` 는 **바인딩되지 않는다**(실제 로드가 항상 더 느림). 이 경우 값 자체는 체감에 영향이 없으므로 2.5 를 유지한다.
- `T_total < 1.0s` (웜 부팅 상시)이면 로딩 화면 전체가 인위 지연이 된다. **사용자 체감 판정 2문항**으로 결정한다: ① "바가 절반 이상 차기 전에 시선이 바에 도달했는가" → 예 여야 한다. ② "기다린다는 느낌이 들었는가" → 아니오 여야 한다. ②가 예면 2.0 으로, ①이 아니오면 3.0 으로 조정한다.
- **두 문항이 상충할 때(① 아니오 + ② 예 — "시작도 못 봤는데 기다리기까지 했다") 는 ① 을 우선해 3.0 으로 올린다.** 근거: ② 의 대기감은 값을 낮추면 언제든 되돌릴 수 있는 손실이지만, ① 의 "로딩 화면을 인지하지 못했다" 는 이 기획의 검증 가설(§헤더) 자체가 무너진 상태라 값 조정 외의 원인(레이아웃·대비·바 위치, §5)까지 함께 의심해야 한다. 3.0 으로 올린 뒤에도 ① 이 아니오면 원인은 시간이 아니므로 §5 레이아웃을 재검토한다. **단 §2-2-1 의 위젯 지연(1.23s)이 해소되기 전에는 이 상향을 적용하지 않는다** — 그 상태의 ① 아니오는 시간 부족이 아니라 빈 화면이 원인이다.

## §3 `AssetPhaseWeight` — 최종값 **0.9** (실측 확정)

> **이 절은 실측으로 전면 재작성됐다.** 초안은 `0.25` 였고, 그 근거는 "2단계(맵)가 1단계(에셋)보다 3배 무겁다"는 **가정**이었다. §7 **M1** 정적 분석과 런타임 타임스탬프가 **그 가정이 정반대로 틀렸음**을 보였다 — 실제 비율은 `T1 : T2 = 8.8 : 1` 이다. 초안의 "근거 ①·② 절충값" 서사는 폐기한다.

### 3-1. 결정

| 항목 | 값 |
|---|---|
| `USpyLoadingConfig::AssetPhaseWeight` | **0.9** |
| 2단계 가중치 (`1 − W`) | 0.1 |
| 플랜 기본값 | 0.5 (→ 이 기획서가 **0.9** 로 확정) |
| 초안값 | 0.25 (가정 기반 — **실측으로 폐기**) |
| 상태 | **실측 확정.** `DA_SpyLoadingConfig` 에 반영·저장 완료 |

### 3-2. 근거 — 가중치는 "실제 소요 시간 비율"이어야 바가 등속으로 찬다

`Raw` 는 두 단계의 가중합이다. 가중치가 실제 시간 비율과 어긋나면 `Raw` 는 시간에 대해 비선형이 되고, 바는 **한 구간에서 빨리 차고 다른 구간에서 멈춘다**. 즉 **`W ≒ T1 / (T1 + T2)`** 가 정답이다. **이 원칙 자체는 초안(근거 ①)이 옳았고, 실측은 그 원칙을 확인하면서 대입할 숫자만 뒤집었다.**

**런타임 타임스탬프 (§7 M1)**

| 구간 | 로그 | 소요 |
|---|---|---|
| `T1` — 로딩 시작 → 1단계 완료 | `16:17:16.244 로딩 시작 — 1단계 대상 12 개` → `16:17:18.969 Batch Async Load Complete (12)` | **2.725s** |
| `T2` — 1단계 완료 → 맵 전환 | → `16:17:19.277 게임플레이 맵 전환` | **0.308s** |
| (참고) `T3` — `OpenLevel` 실소요 | `16:17:19.444 LogLoad: Took 0.147283s to LoadMap(DevMap)` | **0.147s** |

**검산**: `T1 / (T1 + T2) = 2.725 / (2.725 + 0.308) = 2.725 / 3.033 = 0.8985` → **`W = 0.9`** (0.05 단위 반올림). 비율로는 **8.8 : 1**.

**측정 조건과 한계 (그대로 기록한다)** — 이 실행은 진짜 Standalone 이 아니라 **멀티플레이 PIE**(리슨 서버 + 클라이언트 2, `UEDPIE_*` 월드)였다. 따라서 (a) 맵이 PIE 복제라 `T2`·`T3` 의 **절대값**은 패키징 빌드와 다를 수 있고, (b) `T1` 구간에 PIE 월드 3개 스핀업이 겹쳐 있어 `T1` 절대값도 부풀려졌을 수 있다. **그럼에도 비율 8.8:1 은 신뢰한다** — 아래 §3-3 의 정적 참조 분석이 런타임과 **독립적인 방법**으로 같은 방향(2단계에 로드할 것이 거의 없음)을 가리키기 때문이다. 절대값은 잠정으로 두고 패키징 빌드에서 재확인한다(§3-5).

### 3-3. 왜 이렇게 되는가 — `DevMap` 폐포가 1단계 폐포에 포함된다

런타임 비율은 우연이 아니라 **참조 구조의 필연**이다. §1-2 의 정적 분석(AssetRegistry, 하드+소프트 참조 폐포):

| | 패키지 | 크기 |
|---|---|---|
| 1단계 (이름 맵 12개 루트의 폐포) | 225 | 207.6 MB |
| 2단계 (`DevMap` 폐포) | 120 | 185.6 MB |
| 겹침 | 115 | 185.4 MB |
| **2단계 고유 (하드 참조만)** | **5** | **0.2 MB** |
| **2단계 고유 (소프트 참조 포함)** | **0** | **0.0 MB** |

- 2단계 고유 5개의 정체는 `BP_SpyGameMode` · `DevMap` 자체 · StarterContent 3개(`M_Basic_Wall` · `Shape_Cube` · `Shape_Sphere`) — 합쳐 **0.2 MB**.
- 겹치는 185 MB 의 정체는 **Manny 캐릭터 자산**(`SKM_Manny` 27MB + `T_Manny_*` 20/17/13/12/10MB…). `BP_SpyCharacter`(1단계 루트)와 `DevMap`(2단계)이 같은 것을 참조한다.

**결론: 1단계가 끝나면 2단계는 로드할 것이 사실상 남아 있지 않다.** 그래서 `T2`(0.308s)는 "맵을 읽는 시간"이 아니라 거의 전부 **이미 상주한 패키지를 확인하는 시간**이다. 이 구조가 유지되는 한 `W` 는 0.9 근처가 정상이며, 0.5 나 0.25 는 **바의 절반~3/4 을 0.3초짜리 구간에 할당하는** 설정이 된다.

### 3-4. 기각된 근거 — "정체는 낮은 지점에서 생겨야 한다" (초안 근거 ②)

초안은 "`W` 는 바가 멈춰 보일 수 있는 높이이므로 낮아야 한다(25% 정체는 자연스럽고 50% 정체는 먹통으로 읽힌다)"를 두 번째 근거로 들었다. **이 논거는 기각한다.**

- `W = 0.9` 에서 1단계는 **바의 90% 를 차지하는 본 구간**이다. 1단계 완료 직후 남는 것은 마지막 10% 뿐이므로 "1단계 완료 후 `W` 높이에서 멈춰 보인다"는 시나리오는 **"바가 90% 에서 잠깐 멎었다가 끝난다"** 가 되고, 이는 정체가 아니라 **정상적인 마무리 구간**이다.
- 더 근본적으로, 초안 근거 ② 는 "1단계가 순식간에 끝나고 2단계가 오래 걸린다"는 **틀린 전제 위에서만** 성립했다. 전제가 뒤집혔으므로 논거 자체가 성립하지 않는다.
- 초안이 이 논거의 검증용으로 뒀던 **M1-b(정체 관찰) 는 삭제**한다.

대신 `W = 0.9` 에서 새로 생기는 것은 **1단계 카운터의 계단**이다: 대상이 12개이므로 에셋 1개 완료마다 `Raw` 가 `0.9 / 12 = 0.075` (**7.5%p**) 씩 뛴다. 그리고 `T1 = 2.725s > MinDisplaySeconds = 2.5s` 이므로 **후반부에서는 시간 램프가 아니라 `Raw` 가 상한**이 되어 이 계단이 화면에 노출된다. 7.5%p 는 §4-3 이 정한 보간 전환 임계치(**단일 프레임 15%p 초과**)의 절반이므로 **§4 의 "보간 없음" 결정은 유지**된다. 다만 이 계단은 §7 **M2** 의 관찰 대상으로 남는다.

### 3-5. 대안 비교 (실측 반영)

| 안 | `W` | 시간 비율(실측 8.8:1) 정합 | 화면에서 벌어지는 일 | 판정 |
|---|---|---|---|---|
| A | 0.5 (플랜 기본) | **불리** — 0.9 와 0.4 어긋남 | 2.7초 걸리는 1단계에 바의 절반만, 0.3초 걸리는 2단계에 나머지 절반을 배정 → 바가 전반 내내 느리다가 끝에서 50%p 를 순간에 채움 | 기각 |
| B | 0.25 (초안) | **크게 불리** — 0.65 어긋남 | 위 왜곡이 3배로 심해짐. 2.7초 동안 바가 25% 까지만 오른다 | 기각 (실측으로 폐기) |
| **C** | **0.9** | **일치** — `0.8985` 의 0.05 단위 반올림 | 바가 실제 로드 진척과 같은 속도로 오르고, 마지막 10% 가 맵 전환 구간에 대응 | **채택** |
| D | 1.0 | 비율상으론 근사 | 2단계가 진행률에 **전혀** 안 잡혀, 맵 로드가 느려질 때 바가 100% 인 채로 멈춘다 — 퇴화 설정 | 기각 (§3-6 상한 근거) |

### 3-6. 재조정 메트릭 — **M1-a (재측정 시 적용)**

- **콜드 부팅(재부팅 후 첫 실행) 측정치만 `W_measured` 입력에 사용한다.** 웜 측정에서는 `로딩 시작` 과 `Batch Async Load Complete` 가 **같은 밀리초에 찍히는 것이 실측으로 확인**됐다(`T1 ≈ 0`). 그 값을 입력에 넣으면 `W_measured → 0` 이 되어 퇴화 설정을 지시한다 — 초안의 "콜드만 사용" 규칙은 이 실측으로 정당성이 확인됐으므로 유지한다.
- 콜드 측정으로 `W_measured = T1 / (T1 + T2)` 를 계산하고, **`|W_measured − 0.9| > 0.10` 이면** `AssetPhaseWeight` 를 `W_measured` 의 0.05 단위 반올림값으로 갱신한다. 그 이하 편차는 시간 램프·계단 해상도에 흡수되므로 갱신하지 않는다.
- **하한 `0.15`** — 유지. 이보다 낮으면 1단계가 진행률에 사실상 잡히지 않는다.
- **상한 `0.95`** — 초안의 상한 `0.5` 는 **정답(0.9)을 배제하고 있었으므로 폐기**한다. `1.0` 을 금지하는 이유는 §3-5 안 D — 2단계가 진행률에 전혀 반영되지 않아 맵 로드가 느려질 때 바가 100% 에서 멈추기 때문이다.
- **재측정 트리거** — ① 패키징 빌드 또는 진짜 Standalone 최초 실행 시(§3-2 의 측정 조건 한계 해소), ② `SpyAssetData` 이름 맵 루트가 추가·삭제돼 §3-3 의 폐포 포함 관계가 깨질 때, ③ `DevMap` 이 1단계 폐포 밖의 대형 자산을 새로 참조할 때.

## §4 로딩바 체감 — **위젯 보간 없음**

### 4-1. 결정

`USpyLoadingWidget` 은 받은 `Displayed` 값을 **그 프레임에 그대로** `LoadingBar->SetPercent()` 에 넣는다. 위젯 측 lerp/보간·자체 틱을 **넣지 않는다.**

### 4-2. 근거 — 매끄러움은 이미 구조가 보장한다

- **상승 속도에 상한이 있다.** `Displayed = min(Raw, Elapsed / 2.5)` 이므로 시간 램프가 상한인 구간에서 프레임당 증가는 최대 `1/(2.5 × 60) = 0.667%p` (60fps). 768px 바(§5-2)에서 **프레임당 5.1px** (`768 × 0.006667 = 5.12`) — 등속 애니메이션과 구분되지 않는다.
- **초반의 `Raw` 점프는 램프에 눌린다.** 웜 부팅에서 1단계가 `StartLoading` 스택 안에서 동기 완료돼 `Raw` 가 0 → 0.9 로 계단 점프해도, 그 시점의 램프 상한(예: t=0.1s → 4%)이 실제 표시값을 결정한다. **이 계단은 화면에 나타나지 않는다.**
- **후반의 계단은 노출되지만 임계치 아래다.** 콜드 부팅 실측(`T1 = 2.725s > MinDisplaySeconds = 2.5s`, §3-2)에서는 후반부에 `Raw` 가 상한이 되어 1단계 카운터의 계단이 그대로 보인다. 그 크기는 `0.9 / 12 = 0.075` (**7.5%p**) 로 §4-3 의 보간 전환 임계치(15%p)의 절반이다 (§3-4).
- **역행이 없다.** `Tick` 이 `NewDisplayed > DisplayedProgress` 일 때만 반영하므로 단조 증가가 코드 레벨에서 보장된다(plan Task 4 Step 5). 보간의 대표 용도인 "역행 흡수"가 애초에 불필요하다.
- **보간은 오히려 해롭다.** 전환은 `Displayed = 1.0` 브로드캐스트와 **같은 프레임에** `OpenLevel` 을 호출한다(§1-2). 위젯이 보간 중이면 화면에 그려진 값은 100% 에 못 미친 상태로 잘려 나간다 — "바가 다 차지 않았는데 넘어갔다"는 최악의 인상이 된다.
- **아키텍처 정합** — spec §4-3 은 위젯을 "순수 뷰"로 규정한다. 보간은 위젯에 상태·틱을 추가해 이 경계를 흐린다.

### 4-3. 남는 위험과 대안 (조건부)

램프가 아니라 `Raw` 가 상한인 구간(콜드 부팅 후반)에서는 `GetAsyncLoadPercentage` 의 해상도가 그대로 노출돼 **계단·정체**가 보일 수 있다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (채택)** | 보간 없음 | 100% 도달이 전환 프레임과 정확히 일치. 위젯이 순수 뷰로 유지 | `Raw` 가 상한인 구간의 계단이 그대로 보임 |
| B (조건부 대안) | 위젯에서 **등속** 보간 — 표시값을 목표값 쪽으로 **초당 1.5** (전체 구간 0.67초) 로 접근 | 계단을 0.1s 내로 뭉갬 | 전환 프레임에 표시값이 목표에 못 미칠 수 있음. 위젯에 틱·상태 추가 |
| C (기각) | 서브시스템에서 평활 | 뷰는 그대로 | 확정된 `Displayed` 공식(spec §5)을 수정하는 것 — **구조 변경이므로 이 기획서의 권한 밖** |

**전환 임계치** — §7 **M2** 에서 Standalone 화면 캡처를 검토해 **① 단일 프레임 증가폭 > 15%p 이거나 ② 0.5초 이상 완전 정지**가 관찰되면 B 로 전환한다. 그때도 감쇠(`FInterpTo`) 가 아니라 **등속(constant) 보간**을 쓴다 — 감쇠는 목표에 점근할 뿐 도달하지 않아 100% 를 못 찍는다. 위 두 조건 중 어느 것도 관찰되지 않으면 A 를 유지한다.

## §5 퍼센트 표기 · 화면 레이아웃

> **가정 표시** — 이 절의 색·서체·형태는 컨셉서 §1 "세부 톤·레퍼런스"가 `(사용자 확정 대기)` 인 상태에서, **"차갑고 절제된 첩보 계측기(instrument readout)"** 라는 톤 가정 위에 세운 **작업값**이다. 값 자체는 전부 구체적으로 확정해 두되(구현이 멈추지 않도록), 톤 확정 시 §5-4 절차로 갱신한다.

### 5-1. 퍼센트 텍스트 표기 규칙

| 항목 | 결정 |
|---|---|
| 산출값 | `FMath::RoundToInt(Displayed × 100)` — **spec §5 그대로, 변경 없음** |
| 렌더 포맷 | **3자리 zero-pad + `%` 기호** — `%03d%%` |
| 렌더 결과 | `0` → **`000%`** / `7` → **`007%`** / `42` → **`042%`** / `100` → **`100%`** |
| 로케일 그룹 구분자 | **사용하지 않는다** (0~100 범위라 어차피 발생하지 않지만, 숫자 포맷팅 대신 고정 포맷 문자열을 쓴다) |
| 서체 | `/Engine/EngineFonts/Roboto`, Regular |
| 크기 | **28** (1920×1080 디자인 해상도 기준) |
| 색 | `#E6F4F6`, 불투명도 **0.85** |
| 정렬 | **우측 정렬** — 바의 오른쪽 끝에 맞춘다 |

**근거** — 자릿수를 3자리로 고정하는 이유는 **정렬 안정이 아니라 톤**이다(Roboto 는 숫자가 등폭이라 자릿수가 변해도 폭이 흔들리지 않는다). `007%` 는 사람이 읽으라고 만든 숫자가 아니라 **장비가 뱉는 계측값**처럼 읽힌다 — 첩보 장비·터미널 리드아웃의 관용이고, 컨셉서 §1 "스파이 테마"와 정합한다. `%` 기호는 유지한다: 3자리 고정만으로는 `042` 가 퍼센트인지 다른 코드값인지 구분되지 않는다.

**대안 비교**

| 안 | 예시 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | `42` (플랜 기본) | 가장 단순 | 단위 부재로 의미가 모호. 톤이 없음 | 기각 |
| B | `42%` | 표준적·명확 | 범용 애플리케이션 톤. 스파이 색이 없음 | 기각 |
| **C** | **`042%`** | 계측기 톤. 단위 명확 | 익숙하지 않아 낯설 수 있음 | **채택** |
| D | `042` | 가장 장비 같음 | 단위 부재 — B 의 단점을 그대로 안음 | 기각 |

### 5-2. 화면 레이아웃

디자인 해상도 **1920×1080** 기준. 좌표는 Canvas Panel 앵커/정렬 기준.

| 요소 | 앵커 | 정렬(Alignment) | 위치 | 크기 |
|---|---|---|---|---|
| 배경 (`Border`, 단색) | 전체 채움 (0,0)~(1,1) | — | Offset 0 | 화면 전체 |

**z-order (배치 순서) — 반드시 지킬 것.** 배경 `Border` 는 Canvas Panel 의 자식 목록에서 **`LoadingBar` · `PercentText` 보다 먼저(위쪽 = 뒤에 그려짐)** 놓는다. UMG 는 자식 목록의 **나중 항목을 위에** 그리므로, 배경을 마지막에 추가하면 바와 텍스트를 통째로 덮어 **화면이 검게만 나온다.** 배치 순서: ① 배경 `Border` → ② `LoadingBar` → ③ `PercentText`. (plan Task 7 Step 2 는 위젯 트리를 사람이 손으로 구성하도록 지시하므로 순서를 여기서 못박는다.)
| `LoadingBar` (ProgressBar) | (0.5, 1.0) | (0.5, 1.0) | X `0`, Y **`-120`** | **768 × 6** |
| `PercentText` (TextBlock) | (0.5, 1.0) | (1.0, 1.0) | X **`+384`**, Y **`-134`** | Auto |

- `PercentText` 의 X `+384` 는 바 폭 768 의 절반 — **바의 오른쪽 끝과 텍스트 오른쪽 끝이 정확히 맞는다.** Y `-134` 는 바 상단(`-120 − 6 = -126`)보다 **8px 위**다.
- 바를 하단 120px 에 두는 이유: 화면 중앙은 전환 직후 게임플레이 카메라가 차지하는 영역이라, 로딩 UI 를 중앙에 두면 전환 시 시선이 크게 이동한다. 하단 배치는 **HUD 관성**과도 맞는다.
- 바 두께 **6px** — 두꺼운 바는 캐주얼/모바일 톤이다. 얇은 선은 "계측 눈금"으로 읽혀 톤 가정과 맞다. 6px 은 1080p 화면 높이의 **0.56%** (`6 / 1080`) — 하단 120px 위치에서 선으로 식별되면서 "바"가 아니라 "눈금"으로 읽히는 두께다. 이 값은 계산으로 도출한 것이 아니라 톤 가정에 따른 선택이며, §5-4 톤 확정 시 함께 재검토한다.
- 바 폭 **768px** (화면의 40%) — 프레임당 5.1px 증가(§4-2)가 등속 이동으로 지각되는 폭이면서, 화면을 가로지르지 않아 절제된 인상을 준다.

## §6 전환 순간의 UX

### 6-1. 지금 일어나는 일 (실측 기반)

`Raw >= 1.0 && Elapsed >= 2.5` 가 만족된 프레임에 `DisplayedProgress = 1.f` 를 브로드캐스트하고 **같은 프레임에** `OpenLevel` 을 호출한다(§1-2). 즉 **100% 는 사실상 1프레임(≈16ms) 만 화면에 있다.** 이후 화면에는 두 개의 이음매가 생긴다.

| 이음매 | 내용 | 이 기획의 처리 |
|---|---|---|
| **① 로딩 화면 → 레벨 트래블(블랙 프레임)** | `OpenLevel` 직후 로딩 위젯이 사라지고 엔진의 검은 화면이 몇 프레임 지속 | **범위 안에서 해소** — §6-2 |
| **② 레벨 트래블 → 게임플레이 첫 프레임** | 검은 화면에서 밝은 게임 화면으로 하드 컷 | **범위 밖 — 진짜 페이드가 필요하다.** §8 "다음 단계 제안" 으로 분리 |

### 6-2. 이음매 ① 처리 — 배경 휘도 일치 (범위 안, 코드 변경 0)

배경을 `#08090B` (§5-3)로 둔 이유가 여기다. 화면의 대부분이 이미 거의 검정이므로, 로딩 위젯이 사라지고 엔진 블랙 프레임이 들어와도 **바뀌는 것은 하단의 얇은 바와 작은 숫자뿐**이다. 밝은 배경이었다면 같은 순간이 "번쩍 → 암전" 으로 읽힌다. 이건 값 선택만으로 얻는 결과이며 코드도 추가 에셋도 필요 없다.

**"100% 를 못 본다"는 문제는 대부분의 경우 발생하지 않는다.** 시간 램프가 상한인 흔한 경로에서는 `Raw = 1.0` 이 이미 참인 채로 램프가 `Elapsed = 2.5s` 에 정확히 1.0 에 도달하고, 바로 그 순간 전환이 걸린다. 즉 **바는 마지막 픽셀까지 등속으로 차오른 끝에 전환된다** — 이 경우 도착이 시각적으로 완결된다. 문제가 되는 건 콜드 부팅 후반에 `Raw` 가 상한이라 바가 96% 근처에서 정체하다 100% 로 튀며 잘리는 경우이고, 이는 §4-3 의 전환 임계치(단일 프레임 15%p 초과)로 감시한다.

### 6-3. 페이드아웃 — 이 스펙 범위 안에서는 하지 않는다

| 안 | 내용 | 판정 |
|---|---|---|
| A | 위젯 애니메이션 페이드 | 재생 트리거 코드(전환 직전 콜백)가 필요 → 서브시스템↔위젯 결합 추가. **spec §4-3 의 "서브시스템은 위젯을 모른다"를 깬다.** 기각 |
| B | 전환 지연(hold) 후 페이드 | `ShouldTransition` 에 hold 개념을 추가하는 **구조 변경**. 이 기획서의 권한 밖. 기각 |
| **C (채택)** | 페이드 없음 + **배경 휘도 일치**(§6-2) | 코드·에셋 변경 0. 이음매 ① 을 실질적으로 해소 | **채택** |

이음매 ② 를 없애려면 게임플레이 맵 진입 후의 페이드인이 필요하고, 그건 이 스펙이 다루지 않는 게임플레이 맵 쪽 작업이다 → §8.

## §7 검수 계획 · PIE 한계

### 7-1. PIE 에서 판단하면 안 되는 것 (개발자 안내)

> **PIE 에서는 페이싱 수치(`MinDisplaySeconds` · `AssetPhaseWeight`)의 적정성, 바의 정체·계단 여부, 전환 타이밍을 판단하지 말 것** — PIE 는 맵을 `/Temp/UEDPIE_0_...` 로 복제해 열어 2단계가 실측이 아니며(spec §5 "알려진 한계"), 사실상 `MinDisplaySeconds` 페이스로 흐르는 바만 보게 된다. **PIE 에서 검수 가능한 것은 레이아웃·색·퍼센트 문자열 포맷뿐**이고, 페이싱은 반드시 Standalone(또는 패키징) 빌드에서 판정한다.

> **단, 로그 타임스탬프는 예외적으로 PIE 에서도 쓸 수 있다.** §7-3 의 `T1`·`T2` 는 멀티플레이 PIE 에서 수집됐고, **절대값은 잠정**으로 두되 **비율**은 정적 참조 분석(§3-3)이 독립적으로 뒷받침해 채택했다. 이 예외는 "두 방법이 같은 방향을 가리킬 때"에 한한다 — 화면으로 보는 페이싱 판단에는 적용되지 않는다.

| **1단계 프리로드 대상 선별** | 이름 맵 전체가 아니라 "첫 교전까지 필요한 에셋"만 프리로드 | 실측상 1단계가 **2.725초 / 225 패키지 / 207.6 MB** 를 끌어오며 부팅 시간의 90% 를 차지한다(§3-2·§3-3). **선별하면 실질 단축 효과가 있는 유일한 지점**이지만, 무엇을 뒤로 미룰지는 게임플레이 요구(첫 교전까지 필요한 것)를 정의해야 결정되고 그건 컨셉서 §2 코어 루프(`사용자 확정 대기`) 확정 후의 작업이다 |
| **로딩 위젯 클래스 선로딩** | `WBP_Loading` 을 로딩 파이프라인 시작 **전에** 로드해 §2-2-1 의 1.23초 빈 화면을 제거 | 구현 쪽 과제 — 이 기획서는 값이 아니라 **문제의 존재와 영향(2.5초 중 49%가 빈 화면)** 만 기록한다. 해소되면 §2 의 인지 예산 전제가 그대로 성립한다 |

## §9 구현 요청사항

> 이 기능은 **GAS 를 사용하지 않는다.** 아래 "해당 없음" 항목은 누락이 아니라 명시적 부재다.

### 9-1. Gameplay Tag

**해당 없음.** 로딩 씬은 ASC·어빌리티·이펙트를 사용하지 않는다. `SKGameplayTags.h` · `SpyGameplayTags` 어느 쪽에도 태그를 추가하지 않는다.

### 9-2. C++ 인터페이스

**해당 없음.** 신규 `I` 접두사 인터페이스가 필요하지 않다. 클래스 구성은 plan Task 1~6 이 확정한 그대로다.

### 9-3. GA · GE 명세

**해당 없음.** 신규 `GameplayAbility` · `GameplayEffect` · `AttributeSet` 변경이 없다.

### 9-4. DataAsset — **값 지정** (스키마 변경 아님)

`USpyLoadingConfig` 의 필드 구성은 plan Task 2 가 확정했다. 이 기획서는 **`/Game/Spy/Data/DA_SpyLoadingConfig` 에 들어갈 값만** 지정한다.

| 필드 | 값 | 출처 |
|---|---|---|
| `GameplayMap` | `/Game/Spy/Maps/DevMap.DevMap` | plan Task 7 Step 3 (변경 없음) |
| `MinDisplaySeconds` | **`2.5`** | §2 |
| `AssetPhaseWeight` | **`0.9`** | §3 (실측 `T1:T2 = 8.8:1`) — **`DA_SpyLoadingConfig` 에 반영·저장 완료** |

C++ 기본값(`SpyLoadingConfig.h` 의 `= 2.f` / `= 0.5f`)도 위 값(`= 2.5f` / `= 0.9f`)으로 맞춘다 — DataAsset 이 유실돼도 의도한 페이싱이 나오게 한다.

### 9-5. 위젯 — `WBP_Loading` 구성 값

BindWidget 이름(`LoadingBar` · `PercentText`)과 부모 클래스(`USpyLoadingWidget`)는 plan Task 6·7 확정. 아래는 **스타일·배치 값**이다.

- 레이아웃(앵커·정렬·위치·크기): §5-2 표 그대로
- 색: §5-3 표 그대로 (배경 `#08090B` / 미충전 `#1A1F24` / 충전 `#5AC8D8` / 텍스트 `#E6F4F6` @0.85)
- 서체: `/Engine/EngineFonts/Roboto` Regular, 크기 28
- 추가 자식 위젯: **단색 `Border` 1개(배경)만.** 정적 라벨·팁·이미지 없음 (§5-3)
- **배치 순서(z-order): ① 배경 `Border` → ② `LoadingBar` → ③ `PercentText`.** 배경을 나중에 추가하면 바·텍스트를 덮어 화면이 검게만 나온다 (§5-2 z-order 항)

### 9-6. `USpyLoadingWidget` — 표시 규칙 (뷰 로직)

- `LoadingBar` : 받은 `Displayed` 를 **보간 없이 그 프레임에** 반영한다 (§4). 위젯에 틱·자체 상태를 추가하지 않는다.
- `PercentText` : `FMath::RoundToInt(Displayed × 100)` 결과를 **`%03d%%` 포맷으로 렌더**한다 — 출력 예 `000%` / `007%` / `042%` / `100%` (§5-1).
  **plan Task 6 Step 2 의 `FText::AsNumber(Percent)` 는 이 포맷을 만들지 못하므로, 그 한 줄을 아래로 대체한다:**

  ```cpp
  PercentText->SetText(FText::FromString(FString::Printf(TEXT("%03d%%"), Percent)));
  ```

  산출식(`const int32 Percent = FMath::RoundToInt(Clamped * 100.f);`) 자체는 spec §5 · plan Task 6 그대로 유지한다.
